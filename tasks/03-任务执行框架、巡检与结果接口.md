## 1. 目标

落地两个独立线程池、领取 CAS 与状态机、三条巡检与删除清理矩阵、
跨存储成功写入顺序、`expire_at` 顺延、两个查询接口与 `DegradeAccumulator`。

## 2. 范围

- 要修改的模块：`task`、`api`、`cache`
- 允许修改的接口：新增 `ExecutorConfig`（业务线程池，不是中间件配置类）、`TaskStateService`、
  `TaskSweepJob`、`CleanupJob`、`TaskDeleteService`、`DELETE /api/health-report/task/{taskId}`、
  `GET /api/health-report/task/{taskId}`、`GET /api/health-report/result/{taskId}`、`DegradeAccumulator`
- 允许修改的数据库表/字段：`status`/`stage`/`progress`/`heartbeat_at`/`deadline_at`/`version`/
  `expire_at`/`deleted_at`/终态字段；物理删除 file 行
- 允许修改的 Prompt/Schema/常量：无

## 3. 功能要求

### A. 线程池与状态机（原 07）

1. **两个线程池必须分开**：`analysisExecutor`（任务池，W 个线程）与 `llmBatchExecutor`（批次池，W×4）。
   **共用一个池会线程饥饿死锁**，且心跳正常、巡检扫不出来。
2. 任务池：固定 W 线程 + `ArrayBlockingQueue` **有界** + `AbortPolicy`。
   **不得**用无界队列 / `CallerRunsPolicy` / 静默丢弃（§4.2 三条理由各对应一种线上事故）。
3. `submit` 在**事务提交之后**执行（任务 02 已建好事务边界）；被拒或抛异常 →
   事务外把任务 CAS 为 `FAILED/SERVER_ERROR` → 接口返回 `SERVER_ERROR`。
4. 工作线程第一件事是领取 CAS：
   `UPDATE ... SET status='PARSING', heartbeat_at=now(), deadline_at=now()+10min, version=version+1
    WHERE task_id=? AND status='QUEUED' AND deleted_at IS NULL`。
   **影响 0 行 → 直接结束，不做任何事、不写终态**。
5. `stage` 只有三个取值：`UPLOADING`(QUEUED,0~30%) / `PARSING`(PARSING+EXTRACTING,30~80%) /
   `ASSEMBLING`(ASSEMBLING,80~100%)。**`EXTRACTING` 不作为 stage 出现**。
   每阶段进入时写区间起点，**后端不做区间内细粒度递增**。
6. 心跳每 30s 更新 `heartbeat_at`，**由独立调度线程执行**（批次并行等待期间主流程是阻塞的）。
   **心跳只更新 `heartbeat_at`，绝不顺延 `deadline_at`**。
7. `W = min(floor(C/(4×实例数)), floor((堆预算 - Web层占用)/单任务峰值))`，两个上界取小。
   本任务把两者做成可配置项并在启动时打日志。

### B. 巡检、删除与清理（原 08）

8. **三条巡检并列**（每 5 分钟，xxl-job），`fail_code` **不得混用**：
   ① 心跳超时 15 分钟 → `SERVER_ERROR`（没人在跑了）
   ② `now() > deadline_at` → `EXECUTION_TIMEOUT`（在跑但跑不完）
   ③ `QUEUED` 超过 5 分钟 → `SERVER_ERROR`（提交线程池前崩溃）
   三条都置 `reanalyzable = 1`。
9. 删除四步（§4.5）：置 `deleted_at` → 删对象存储/file 行/Redis 结果 →
   **【不中断】已在跑的工作线程**（不 `Future.cancel`、不发中断）→ 写回时被 `deleted_at IS NULL` 拦下。
   **正确性靠写回条件保证，不靠能不能及时停下来。**
10. 清理任务**按状态逐类判定**，不能笼统「终态即删」（§4.5 的六行矩阵）。
    **原文件在任务整体 `SUCCEEDED` 后才删**，`FAILED` 且 `reanalyzable=1` 时保留至 `expire_at`。

### C. 成功写入顺序与查询接口（原 09）

11. **成功写入顺序不可调换**（§4.4）：
    ① 写 Redis `result:{taskId}`（TTL 2h，此时**结果尚不可见**）
    ② MySQL CAS `ASSEMBLING → SUCCEEDED`
    ③ CAS 影响 0 行 → **立刻 DEL Redis 结果**，再按原因写终态
    **反过来做（先 CAS 再写 Redis）有真实坏窗口**：状态成功而结果缺失，且状态机无回边、重试不了。
12. 成功 CAS 的 **四个 WHERE 条件缺一不可**：
    `status='ASSEMBLING'` / `deleted_at IS NULL` / **`deadline_at >= now()`** / 同时 `expire_at = now()+2h`。
    **`deadline_at >= now()` 不能省**，否则超时后、巡检跑到前的窗口里任务照样能成功。
13. **`expire_at` 只在成功时顺延为 2 小时**，与结果 TTL 对齐；`FAILED` 的 30 分钟不变。
14. `GET task/{id}` 只返状态，**不返结果**；`QUEUED` 必须能返回。
15. `GET result/{id}` 读取顺序：查 MySQL → 四种情况同码 `404 RESULT_EXPIRED` →
    `status != SUCCEEDED` 返 `409 TASK_NOT_FINISHED`（**不读 Redis**）→ 才读 Redis。
16. `DegradeAccumulator`（§6.2.3）：三个布尔只增不减；
    **抑制标志按 OR 累积，与 `partial_reason` 取哪一个完全无关**；
    `primaryReason()` 返回 `PartialReason` 枚举（**不返回字符串、不出现魔法字符串**），按严重度取。
17. `result` 接口必须下发 `partial` / `partialReason` / `suppressDietAdvice` / `suppressDishRecommend` /
    `processedPages` / `totalPages`，**四个开关字段全部取自 `DegradeAccumulator`**。

## 4. 验收条件

- [ ] 正常场景：任务从 QUEUED 走到 ASSEMBLING，`stage`/`progress` 按表映射；成功任务能读到结果
- [ ] 边界场景：**R33a** —— `QUEUED` 时 task 接口返回 `stage=UPLOADING`、`progress=0`
- [ ] 边界场景：**R33b** —— `stage` 只有三个取值，`EXTRACTING` 不出现
- [ ] 边界场景：**R41** —— 心跳超时与 deadline 超时的 `fail_code` 分别是 `SERVER_ERROR` 与 `EXECUTION_TIMEOUT`
- [ ] 边界场景：**R38** —— 成功后第 31 分钟仍能读到（`expire_at` 已顺延）
- [ ] 边界场景：**R40a** —— 任务未完成时调 result 接口返 `409 TASK_NOT_FINISHED` 且**不读 Redis**
- [ ] 失败场景：**R34** —— `submit` 抛 `RejectedExecutionException` → 任务 `FAILED/SERVER_ERROR`，接口返 `SERVER_ERROR`
- [ ] 失败场景：**R35** —— 任务已删除后领取 CAS 影响 0 行，**不做任何事、不写终态**
- [ ] 失败场景：`deleted_at` 一旦非空不可改回（§3.1.2 的 B7 唯一执行点）
- [ ] 失败场景：**R36** —— `deadline_at` 已过但巡检未跑，成功 CAS 影响 0 行 → 删 Redis 结果 → `FAILED/EXECUTION_TIMEOUT`
- [ ] 失败场景：**R37** —— 写 Redis 后、CAS 前崩溃，结果**不可见**
- [ ] 失败场景：**R43d/R43e** —— 多个降级原因组合时抑制标志按 OR 累积，`partialReason` 按严重度取；
      **模块三不得因后命中的过敏原因被重新输出**
- [ ] 幂等/并发场景：重复 submit 同一 taskId 只有一次能领取成功；删除与工作线程写回并发时结果**不会在删除后重新出现**
- [ ] 安全与日志：**R50** —— `SUCCEEDED` 后原文件与 file 行立即删
- [ ] 安全与日志：**R51** —— `FAILED` 且 `reanalyzable=1` 时原文件**保留**至 `expire_at`（否则「重新解析」形同虚设）
- [ ] 安全与日志：**R48** —— Redis 结果**不含**姓名、性别、完整 OCR 文本；记录状态迁移但**不记录任何报告内容**
- [ ] Java 8 全量构建通过：是

## 5. 不做什么

- 本任务不包含：真正的解析逻辑（工作线程内先放 sleep 占位）、四模块的真实内容（先用占位结构）
- 不允许新增：任何消息队列 / outbox / Dispatcher；任何中断或取消工作线程的机制；
  任何从 `partial_reason` 反推抑制标志的逻辑
- 不允许改变的既有行为：状态机必须纯单向无回边

## 6. 外部依赖与已确认决定

- 外部接口/凭证/测试数据：模型并发配额 C 待确认，测试用配置值；xxl-job 调度，测试直接调 Service 方法；
  Redis（可用嵌入式或 Testcontainers，说明选择）
- 产品已确认决定：重启即失败、不自动恢复（§4.3）；多实例不得在启动时把非终态任务一次判失败；
  四种失败同码不泄露差异
