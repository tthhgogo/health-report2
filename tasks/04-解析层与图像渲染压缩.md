## 1. 目标

落地不可变 `Segment` 与文本规范化、PDF 绘制单元切分与密度闸、OFD/Word 切分与容量闸、
一次渲染两个消费者的图像链路（LLM-A 两档压缩、OCR 独立编码、`effectiveOcrImageBytes`、
bbox 坐标契约与 EXIF 变换）。

## 2. 范围

- 要修改的模块：`parse/segment`、`parse/pdf`、`parse/ofd`、`parse/word`、`parse`
- 允许修改的接口：新增 `Segment`、`BBox`、`TextSource`、`TextNormalizer`、`PdfSegmentParser`、
  `GlyphDensityGate`、`OfdSegmentParser`、`WordSegmentParser`、`WordCapacityGuard`、
  `LlmAImageCompressor`、`CompressedPageImage`、`OcrImageEncoder`、`ExifOrientationTransform`、
  `OcrCapacityCalculator`
- 允许修改的数据库表/字段：**无**——`Segment` 只活在内存，**没有 segment 表**
- 允许修改的 Prompt/Schema/常量：新增 `RadicalNormalizeMap` 常量类

## 3. 功能要求

### A. Segment 模型与文本规范化（原 10）

1. `Segment` **不可变**，字段：`segmentId`（`f{fileIndex}-p{page}-s{seq}`）、`rawText`、
   `normalizedText`、`textSource`（`NATIVE`/`OCR`）、`bbox`。
2. **`rawText` 一个字都不动**（展示与原文核对用）；`normalizedText` 走
   `NFKC → RadicalNormalizeMap（U+2E80–U+2EFF，约 30 条）→ 全角转半角`。
3. **NFKC 只解决一半**：康熙部首区（U+2F00–U+2FD5）有兼容分解会被还原，
   **CJK 部首补充区（U+2E80–U+2EFF）没有**，必须手工映射表。
4. `bbox` 的契约是**原始渲染图上的像素坐标，原点左上、Y 向下**（§5.6.6）；各来源的转换在各自解析器里做。
5. 记 `residualNonStandardCount`，**只记计数不记原文**。

### B. PDF 解析与密度闸（原 11）

6. 一个 segment = **一次 `Tj` / `TJ` 显示操作**。实现路径：**覆写 `PDFStreamEngine` 的
   `showTextString` / `showTextStrings`**。
7. **绝对禁止使用 `PDFTextStripper`** —— 它内部按行聚类，正是 `AGENTS.md` §3 点名的
   「按 Y 坐标聚类成逻辑行」。用它等于把版面判断做回 Java。
8. **解析器不做**：不按字体/基线/字距/坐标二次合并、不识别表格、不聚类行列、不判断单元格。
   哪些块属于同一行由 LLM-A 判断。
9. `bbox` 转成**渲染图左上原点像素坐标**：乘渲染缩放 + **Y 轴翻转**
   （PDF 用户空间原点在左下、Y 向上）。旋转按页面 `/Rotate` 在渲染阶段归一化。
10. **密度闸**（§5.3）：某文件 `segment 数 / 等效页数 > MAX_SEGMENTS_PER_PAGE`（暂定 400）→
    判为逐字形绘制 → **该文件整体改走 OCR 路径**，`textSource` 记为 `OCR`，记 `glyphLevelPdfCount`。
    **不退化为字形块**（会撞破 `blockRefs` 上限、输入体积、`seq` 容量三个硬约束）。

### C. OFD 与 Word 解析（原 12）

11. OFD：一个 segment = ofdrw 的一个**原子文本对象**；不合并。
    `bbox` 换算到**渲染图左上原点像素坐标**（OFD 页面单位 → 像素，按需翻转）。
12. Word：一个 segment = 一个段落；表格按 POI 的**显式 `<w:tc>`** 切。
    **不合并跨行/跨列单元格、不重排行列**。`bbox = null`（Word 无版面坐标）。
13. Word 内嵌图片：**≥300×300px 的提取出来走 OCR，产出的识别块也是 segment**；
    <300×300px 视为装饰图忽略。**图片本身不发给 LLM-A**——
    `BatchPage.imageRequired` 对 Word 全部逻辑页恒为 `false`、`jpegBytes` 恒为 `null`。
14. `WordCapacityGuard`：工作线程解析完按**真实 segment 数**判
    `segment ≤ 1200 且 内嵌图片 ≤ 30`，超出 → `FAILED / PAGE_LIMIT_EXCEEDED`、`reanalyzable=false`，
    **LLM-A 调用次数为 0**。Word 是「超限即拒绝」，**不走截断**。
15. Word 内嵌图片原始字节超 `effectiveOcrImageBytes` → `IMAGE_TOO_LARGE`，
    **不静默跳过那张图**（跳过等于悄悄丢掉报告的一部分）。

### D. 图像渲染、压缩与 OCR 编码（原 13）

16. **渲染按 OCR 档**（300 DPI，A4 约 2480×3508，长边上限 3600px），**不是按 LLM-A 的 2000px**
    ——OCR 是识别精度的源头，掉的字后面全链路补不回来。LLM-A 那档是从这张图**降下来**的。
17. 一次渲染两个消费者：`OcrImageEncoder`（不压质量）与 `LlmAImageCompressor`（降采样+压缩），
    **然后立即释放 `BufferedImage`**（26~39MB/页，攒着必 OOM）。
18. `LlmAImageCompressor` 两档**固定不可调**：
    档1 长边 2000px / quality 0.85；超 1MB → 档2 长边 1600px / quality 0.80；仍超 → `ImageTooLargeException`。
    返回 `CompressedPageImage{jpegBytes, width, height}`——**必须返回实际宽高**，bbox 换算要用。
19. `OcrImageEncoder`：**PNG 无损优先**，超 `effectiveOcrImageBytes` → 回退 JPEG q0.95，
    再超 → `ImageTooLargeException`。**绝对不能复用 LLM-A 的压缩图给 OCR。**
20. 大图不得整幅解码（§5.6.3）：`ImageReader` 只读尺寸 → 超限立即拒 →
    发 LLM-A 的图用 `ImageReadParam#setSourceSubsampling` **降采样解码**。
    OCR 接口锁定为 `recognize(byte[] encodedImageBytes)`，上传图与 Word 图**直接传编码字节，本地不解码**。
21. 压缩实现细节（§5.6.4）：不放大 / PNG 铺白底 / 统一 `TYPE_INT_RGB` /
    **固定 `VALUE_INTERPOLATION_BILINEAR`** / 方向在渲染阶段归一化 / `ImageWriter` 等 finally 释放。
22. `OcrCapacityCalculator`：按 §5.6.2.1 从 `ocr.maxEncodedImageBytes` 与 `ocr.maxRequestBodyBytes`
    推出 `effectiveOcrImageBytes`，**全部用 `long`**（`int` 在 2GB 处溢出成负数，会让上限判断恒为假）；
    启动自检：两个上限 ≤0 或请求体上限 ≤ 协议开销 → **启动失败**。
23. `bbox` 契约（§5.6.6）：各解析器已转成**渲染图左上原点像素**；本段只做
    **原始渲染图 → 压缩图**的等比缩放，**没有 Y 轴翻转**（两边都是左上原点）。
24. `ExifOrientationTransform`：8 个 `Orientation` 值各对应一个固定旋转/镜像矩阵，5~8 时宽高互换。

## 4. 验收条件

- [ ] 正常场景：含部首区字符的文本被正确规范化；一行表格指标被切成多个独立块，可由 `segmentIds` 重新聚合；
      OFD 与 DOCX 各产出正确的 segment 序列
- [ ] 正常场景：**R66** —— 3000×4000 图输出长边 2000px、≤1MB、**全程不落盘**
- [ ] 边界场景：U+2F00–U+2FD5 由 NFKC 还原；U+2E80–U+2EFF 由映射表还原
- [ ] 边界场景：**R42** —— 每页 segment 数 > 400 时该文件整体改走 OCR，`glyphLevelPdfCount` +1
- [ ] 边界场景：**R43b6a** —— `exactSegmentCount` 恰好 1200、图片恰好 30 张，**通过**
- [ ] 边界场景：**R43b6b** —— 原生 1200 + 10 张图，OCR 后超限 → 上传**通过**、工作线程**拒绝**（两阶段独立）
- [ ] 边界场景：**R66a** —— 回退档 2；再超限 → `FAILED / IMAGE_TOO_LARGE`（**不是 `UNREADABLE`、不是 `SERVER_ERROR`**）
- [ ] 边界场景：**R66c** —— 档 2 回退后 bbox 按**实际输出尺寸**换算，不按 2000 硬算
- [ ] 边界场景：**R66f** —— PDF 与 OCR 两条路径的 bbox 都是左上原点像素、指向同一位置；**OCR 不得再翻 Y**
- [ ] 边界场景：**R66h1** —— 8 个 `Orientation` 值的坐标变换逐一正确，5~8 断言宽高互换（**纯本地数学**）
- [ ] 边界场景：**R66i** —— `OcrImageEncoder` 输出**不是** `LlmAImageCompressor` 的产物
- [ ] 失败场景：**R6** —— ArchUnit 断言 `parse` 包不存在 `PDFTextStripper` 引用、不存在按坐标聚类的方法
- [ ] 失败场景：**R43b3** —— OCR 后 `exactSegmentCount=1201` → `FAILED/PAGE_LIMIT_EXCEEDED`，LLM-A 调用 0 次
- [ ] 失败场景：**R43b5** —— Word OCR 服务调用失败 → `SERVER_ERROR`、`reanalyzable=true`，**不得误报 `PAGE_LIMIT_EXCEEDED`**
- [ ] 失败场景：**R66d** —— Word 含内嵌图片时 `jpegBytes` 恒为 `null`、`imageRequired` 恒为 `false`
- [ ] 失败场景：**R66e** —— 渲染失败 → `FAILED / UNREADABLE`，**不抛 `IllegalStateException`**
- [ ] 失败场景：**R66k** —— OCR 容量参数为 0/负/小于协议开销 → **启动直接失败**
- [ ] 幂等/并发场景：`normalize` 幂等；同一 PDF 两次解析产出相同的 `segmentId` 序列
- [ ] 安全与日志：不记录任何 `rawText` / 正文；`residualNonStandardCount` 只记数量；图像与坐标不进日志
- [ ] Java 8 全量构建通过：是

## 5. 不做什么

- 本任务不包含：OCR 客户端真实调用（占位符 + Fake）、R66b/R66g/R66h（见任务 09 与 §11.5）
- 不允许新增：segment 表或任何持久化；任何坐标聚类、行列推断、表格还原；Word 的图片页；
  任何「临时压缩档位」——两档之外一律失败
- 不允许改变的既有行为：`Segment` 的不可变契约；`precheck_pages` 的上传时口径（任务 02）

## 6. 外部依赖与已确认决定

- 外部接口/凭证/测试数据：需要构造样例 PDF/图（**不得使用真实体检报告**）；`PaddleOcrClient` 占位符用 Fake
- 产品已确认决定：`segmentId` 是进程内主键不落库；PDFBox 2.0.x 不升 3.x；
  Word 超限即拒绝、不截断（设计方案 §3.3.1）
- **待验证假设**：PDFBox 能否稳定拿到 `Tj`/`TJ` 绘制单元（§11-19）。
  若实测拿不到，**停止为 BLOCKED**，不要退回 `PDFTextStripper`。
- **⛔ 待接入确认（§0.4）**：OCR 四问——能否吃编码字节 / 是否应用 EXIF / 是否回传图像宽高 /
  单图与请求体上限与编码方式。
  **本任务把两条分支都实现并由必填配置切换，不猜默认值**；配置缺失时启动失败。
  若实现中发现四问的答案会改变接口形状本身，**停止为 BLOCKED**。
- 医疗审核结论：不适用
