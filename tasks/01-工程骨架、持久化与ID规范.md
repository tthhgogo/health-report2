## 1. 目标

建立可编译启动的 Spring Boot 2.7 / Java 8 工程骨架、五个占位符与错误码枚举；
落地三张表的 DDL 与 Entity/Mapper/Service 三件套；
落地 `utf8mb4_general_ci` 大小写不敏感带来的 ID 与归属校验风险兜底。
本任务不实现任何业务逻辑。

## 3. 功能要求

### A. 工程骨架与占位符（原 01）

1. 按开发方案 §1 增补 `pom.xml` 依赖，全部保持 Java 8 / Boot 2.7.18 可编译；新增依赖需在最终消息中说明。
2. 按开发方案 §2 建立包结构：`api/dto`、`task`、`parse/segment`、`llm/a`、`llm/b`、`assemble/sort`、
   `dish`、`safety`、`persistence`、`cache`、`infra`、`support`。空包用 `package-info.java` 占位并写中文类注释。
3. 按开发方案 §10.1 新增五个占位符，只写接口 + 抛 `UnsupportedOperationException`：
   `S3FileStorage`、`DifyClient`、`PaddleOcrClient`、`CurrentUserProvider`、`DishQueryService`。
   **`LlmAModelClient` 不在此列**，它在任务 05 有完整实现。
4. 新增 `support.FailCode` 枚举，取值与开发方案 §9.1 的错误码表**逐条一致**，每个常量带中文注释说明触发点。
5. 新增 `support.PartialReason` 枚举（`PAGE_TRUNCATED` / `BATCH_UNREADABLE` / `ALLERGEN_SUSPECT_MISS`），
   每个常量带中文注释。
6. 新增 `support.SystemActor` 常量类，提供 `HEALTH_REPORT_API` / `HEALTH_REPORT_WORKER` / `DISH_TAG_JOB`
   三个固定标识（开发方案 §3.1.1）。

### B. 三张表 DDL 与持久化层（原 02）

7. 按开发方案 §3.1 建三张表，**逐字对齐**：列名、类型、可空性、`DEFAULT`、`ON UPDATE`、
   逐列 `CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci`、每列中文 `COMMENT`、
   表级 `ENGINE`/`CHARSET`/`COLLATE`/表 `COMMENT`、`PRIMARY KEY` / `UNIQUE KEY` / `KEY`。
8. **表上不写任何 `CONSTRAINT`**：无外键、无 `CHECK`、无触发器（`AGENTS.md` §4）。
9. 产出 `sql/schema.sql`：`CREATE TABLE IF NOT EXISTS`，文件头写明「当前完整结构，可在空库重复执行；
   升级已有环境走 `sql/alter/`」（开发方案 §13.1）。同时建空目录 `sql/alter/` 并放 `.gitkeep`。
10. 实体命名保留 `ct_` 前缀：`CtHealthReportTaskEntity` / `CtHealthReportTaskMapper` / `CtHealthReportTaskService`。
11. `createTime` / `updateTime` 必须标注
    `@TableField(insertStrategy = FieldStrategy.NEVER, updateStrategy = FieldStrategy.NEVER)`；
    **禁止 `MetaObjectHandler`**，禁止任何 SQL / `UpdateWrapper` 写 `update_time = now()`。
12. `createBy` / `updateBy` 取 `SystemActor` 的固定标识，**绝不写用户标识**。
13. 开发方案 §3.1.2 的 B1~B7 七条业务规则，每条在对应 Service 方法上写注释「DDL 无兜底」并留出唯一执行点
    （本任务只建执行点骨架，具体逻辑由后续任务实现）。

### C. ID 规范化与归属校验（原 03）

14. `support.IdCanonicalizer`：`newTaskId()` / `newFileId()` 生成 UUID 的**小写规范形式**；
    `canonicalize(String)` **只断言不静默纠正**——小写化后与原值不等则抛 `IllegalArgumentException`。
15. `task.TaskOwnershipGuard#assertOwned`：校验 `taskId` 归属当前 `userId` 且 `deleted_at IS NULL`。
16. `task.FileOwnershipGuard`：校验每个 `fileId` 的 `user_id == 当前 userId`。
17. **两个 Guard 都必须在 Java 侧做精确 `equals`**，不得只靠 `WHERE user_id = ?`
    ——`_ci` 会把 `Abc` 和 `abc` 判成同一人。
18. 归属校验的四种失败（不存在 / 归属不符 / 已删除 / 已过期）**返回完全相同的结果**，不泄露差异（§4.1）。

## 4. 验收条件

- [ ] 正常场景：`mvn clean verify` 成功，应用可启动；三张表可在 MySQL 8 空库执行成功
- [ ] 边界场景：`FailCode` 与开发方案 §9.1 表格逐条比对，无多无少
- [ ] 边界场景：**R54** —— 解析 `sql/schema.sql` 与开发方案 §3.1 的 DDL 代码块，列级八项 + 表级四项 + 索引三要素逐一相等
- [ ] 边界场景：**R54a** —— `sql/schema.sql` 与「初版 + 全部 alter」两条路径结构一致（当前 alter 为空，断言机制存在即可）
- [ ] 边界场景：`canonicalize` 收到含大写的 ID 时抛异常，**不返回纠正后的值**
- [ ] 失败场景：任一占位符方法被调用时抛 `UnsupportedOperationException`，**绝不返回假数据**
- [ ] 失败场景：`.sql` 中出现 `CONSTRAINT` / `FOREIGN KEY` / `CHECK` / `TRIGGER` 时测试失败
- [ ] 失败场景：`user_id` 大小写不同（`Abc` vs `abc`）时归属校验**失败**
- [ ] 失败场景：**R40** —— 归属校验四种情况返回完全相同的结果
- [ ] 幂等/并发场景：`schema.sql` 可重复执行
- [ ] 安全与日志：**R52** —— 任意实体 insert/update 的 SQL 中不出现 `create_time` / `update_time`；
      不新增任何日志；不写任何中间件或数据源配置类（`AGENTS.md` §5）
- [ ] Java 8 全量构建通过：是
