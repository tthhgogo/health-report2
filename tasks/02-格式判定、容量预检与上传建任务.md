## 1. 目标

落地上传到建任务的完整入口链路：逐格式判定与可读性校验、解压炸弹防御、
`precheck_pages` 容量预检、`POST /file` 上传、`POST /analyze` 任务创建与文件原子绑定。
**`precheck_pages` 在上传时算定，此后全案不再重算**——它是「超 60 页创建前拒绝」唯一可行的落地方式。

## 2. 范围

- 要修改的模块：`parse`、`api`、`task`、`persistence`
- 允许修改的接口：新增 `FormatDetector`、`ReadabilityChecker`、`ZipBombGuard`、`CapacityPrecheckService`；
  新增 `POST /api/health-report/file`、`POST /api/health-report/analyze`
- 允许修改的数据库表/字段：写 `ct_health_report_file`（含 `precheck_pages`）、写 `ct_health_report_task`、
  更新 `ct_health_report_file.task_id`
- 允许修改的 Prompt/Schema/常量：无

## 3. 功能要求

### A. 格式判定与可读性校验（原 04）

1. 按开发方案 §5.1 的表逐格式判定：PDF(`%PDF-`)、JPG/PNG(magic + **实际解码**)、
   DOCX(ZIP + `word/document.xml`)、OFD(ZIP + `OFD.xml`)、DOC(OLE2 `D0CF11E0` + WordDocument 流)。
2. `.zip` 直接拒。DOCX 与 OFD 自身是 ZIP（magic 都是 `PK\x03\x04`），**必须解开查内部结构**才能区分。
3. 可读性校验逐格式实现。**Word 的判据是「正文非空 或 含 ≥1 张 ≥300×300px 的内嵌图片」**
   ——只判正文非空会把「扫描件贴进 Word」这种明确要支持的形态在上传阶段拒掉（§5.1）。
4. 图片的总像素校验**用 `ImageReader` 只读尺寸，不整幅解码**（§5.6.3）——8000 万像素整幅解码是 240~320MB。
5. 解压炸弹防御：**流式计数，不信 `ZipEntry.getSize()`**；累计解压字节或压缩比超阈值立即中断。
6. PDF 文本层判据：抽取字符数/页数 ≥ 50 且非空白占比 ≥ 30%，任一不满足走 OCR。

### B. 容量预检与上传接口（原 05）

7. `parse.CapacityPrecheckService#precheckPages`：
   PDF/OFD 取真实页数；JPG/PNG 恒为 1；DOC/DOCX 取**原生 segment 数 / 40 向上取整的下界**，
   **不做 OCR**、**不建 Segment**（图片型 Word 可为 0）。
8. 上传接口按 §4.1 校验：格式（§5.1）、大小、可读性；
   **JPG/PNG 的上限是 `min(10MB, effectiveOcrImageBytes)`**（§5.6.2.1）——
   `effectiveOcrImageBytes` 本任务先按配置读取，计算逻辑在任务 04。
9. 落 `ct_health_report_file`：`status='UPLOADED'`、`task_id=NULL`、`user_id=当前用户`、
   `expire_at=now+30min`、`precheck_pages`；原文件存对象存储（`S3FileStorage` 占位符，测试用 Fake）。
10. 失败码按 §9.1：`UNSUPPORTED_FORMAT` / `FILE_TOO_LARGE`（**含图片总像素超限**）/ `FILE_UNREADABLE`。

### C. 任务创建与文件原子绑定（原 06）

11. **⓪ 事务外预检**（快速失败）：一次查出全部 `fileId` 的 `precheck_pages` / `size_bytes` / `status` /
    `expire_at` / `task_id`；`SUM(precheck_pages) > 60` → `PAGE_LIMIT_EXCEEDED`，
    `SUM(size_bytes) > 60MB` → `FILE_TOO_LARGE`。**直接返回，不建任务、不绑文件**。
12. **① ~ ④ 事务内**：`INSERT` 任务（`status='QUEUED'`、`expire_at=now+30min`）+ 绑定文件；
    ⓪ 的校验在事务内**重做一遍**（预检是快速失败，事务内那次才是判据，防 TOCTOU）。
13. 绑定用 §4.2 的两步：`SELECT ... FOR UPDATE OF f`（**只锁文件行**，不锁任务行）+
    条件 `UPDATE`（`WHERE ... AND (task_id IS NULL OR task_id = :oldTaskId)`），
    受影响行数必须 == 1，否则整个事务回滚。这是 §3.1.2 的 **B1 唯一执行点**，注释写「DDL 无兜底」。
14. 可绑定条件：`task_id IS NULL` 或（原 task 为 `FAILED` 且 `reanalyzable = 1`）。
15. `FILE_ALREADY_BOUND` **必须返回已绑定的 `taskId`**，兜住响应丢包。
16. `fileIds` 数量 1~5；顺序即 `file_index`（0 起）。**没有队列深度校验**。
17. 文件已过期 → `FILE_EXPIRED`，事务回滚。
18. **顺序不能反**：事务外预检 → 事务内建任务与绑定 → 提交事务 →（线程池提交在任务 03）。

## 5. 不做什么

- 本任务不包含：Segment 产出、线程池提交（任务 03）、状态机流转、解析
- 不允许新增：任何按坐标聚类的逻辑；Word 分支的任何「临时折算系数」——
  若 `precheck_pages` 的 Word 口径与 §4.1.1 冲突，停止为 BLOCKED；
  `SELECT ... FOR UPDATE` 不带 `OF f`（会连带锁任务行，与状态 CAS 争锁）
- 不允许改变的既有行为：`ct_health_report_file` 的 DDL

## 6. 外部依赖与已确认决定

- 外部接口/凭证/测试数据：需要构造样例文件（**不得放入真实体检报告**）；`S3FileStorage` 占位符用 Fake
- 产品已确认决定：HEIC 由前端转 JPEG，后端不引 Native 库；
  Word 走「上传存下界预筛 + 工作线程按真实 segment 数判」（§4.1.2 方案 A）；
  「重新解析」= 同批 fileIds 重调 analyze 接口，不复用 taskId
- 医疗审核结论：不适用
