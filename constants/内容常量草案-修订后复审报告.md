# 《内容常量草案 V2》修订后复审报告

> 复审日期：2026-08-24  
> 复审对象：`constants/内容常量草案.md` 及其当前消费者（README、CSV、Schema、Prompt、开发方案）  
> 复审目标：判断当前内容是否已经足够明确，可直接用于开发与后续医务审核

## 1. 结论

本版相较上一版已有明显改善，尤其是：

- 已把展示内容、Java 硬判定和医学建议分层；
- 已引入 `evidenceLevel`、`matchMode`、`recommendationEligible`；
- 已纠正通用正常词表中的“阴性”；
- 已识别海鲜酱、蟹棒、XO 酱、豆腐钙含量、低钠数据不足等问题；
- 已把高危建议从全局黑名单改为方向矩阵。

但当前版本仍然**不能直接作为开发数据真源，也不能进入医学审核后的上线流程**。主要原因不是待审核项数量多，而是仍有以下三类问题：

1. 草案描述的新结构尚未落到机器数据，现有 CSV、README、Schema、Prompt 仍在使用旧合同；
2. 若干匹配规则存在可复现的漏拦或误拦，尤其是过敏证据覆盖与例外词典；
3. 少数营养和饮食条目的正向推荐口径仍与权威资料或现有菜品数据能力不一致。

本次复审发现 **8 项 P0、9 项 P1、4 项 P2**。其中 P0 应在开发读取常量前解决；P1 应在医务定稿和联调前解决；P2 可在首版上线前收口。

## 2. P0：直接开发或上线阻塞项

### P0-1 新真源尚未形成，当前仓库存在两套互斥合同

草案 §1.2 规定真源为：

- `constants/allergen_registry.csv`
- `constants/advice_registry.csv`

但当前仓库实际仍是：

- 根目录 `allergen_display_split.csv`，只有 `allergenKey/matchWord/displayName/bucket/判定说明` 五列，没有 `evidenceLevel`、`matchMode`、`foodBorne`；
- `constants/README.md` 仍定义旧版三字段 `NutritionContent` 和 `DietRequirementContent`；
- README 仍写“12 个食入性枚举”，并把“阴性”放在 `NormalStatementWords` 中；
- LLM-A/LLM-B Schema 仍使用 `LOW_SUGAR` 和 11 个食入性过敏原；
- LLM-B Prompt 仍使用旧占位符 `recommendIngredients/avoidIngredients`；
- LLM-B Prompt 仍把“海鲜酱（虾）”作为过敏示例，并把“紫菜蛋花汤”固定判为低嘌呤 `REJECT`，与草案修订结论冲突。

这会导致开发人员无法判断应该实现“当前正式合同”还是“草案未来合同”。尤其不能先让 Java 读取旧 CSV，再期待 Prompt 按新结构工作。

**修正要求：**

1. 先定两个 registry 的完整列定义和校验规则；
2. 将草案表格转换为逐行机器数据；
3. 实现生成器并一次性重新生成 Java 枚举、两个 Schema、两个 Prompt 的枚举/占位段、计数和测试夹具；
4. 删除或改写 README 中全部旧结构；
5. 生成结果未落库前，应在草案首页明确写“不可作为运行时真源”，避免被误接入。

### P0-2 `FoodRule` 仍不足以无歧义落库和执行

当前 `FoodRule` 只有：

```text
food / kind / recommendationEligible / matchMode / note
```

但它不能独立表达该条规则属于：

- 推荐食物；
- 避免食物；
- 推荐菜式；
- 避免菜式；
- 烹饪建议；
- 行为建议。

也就是说，如果所有条目统一进入 `advice_registry.csv`，单看一行无法得知它最终应生成 `RECOMMEND`、`REJECT`，还是只展示。依靠文档中的章节位置或列名传递语义，不适合机器真源。

`CATEGORY` 也没有类别成员真源。例如“绿叶蔬菜”“菌菇”“鱼虾”“深海鱼”到底由谁展开、包含哪些标准食材，目前没有定义；如果交给 LLM，就不应再叫确定性的 `CATEGORY` 匹配。

**建议至少补充：**

```text
ruleId
adviceKey
section              RECOMMEND_FOOD / AVOID_FOOD /
                     RECOMMEND_DISH / AVOID_DISH / COOKING_TIP / BEHAVIOR_TIP
value
foodKind
matchMode
recommendationEligible
verdictEffect         RECOMMEND / REJECT / DISPLAY_ONLY
categoryKey           CATEGORY 模式必填
displayOrder
```

同时定义 `matchMode × foodKind × verdictEffect` 的合法组合。否则相同内容可能被不同开发者实现成不同判定行为。

### P0-3 误杀例外词典的当前语义可能造成过敏漏拦

草案 §3.3 定义“先查例外，再查过敏词”，但没有限定例外作用范围。如果例外命中后对整道菜跳过该过敏原，会出现危险漏拦：

- 菜名是“鱼香肉丝”，但配料表确实另含鱼露；
- “蟹黄豆腐”有的用咸蛋黄，有的确实含蟹黄；
- “杏仁豆腐”有的只用香精，有的确实含杏仁；
- 菜名命中例外，但另一条明确食材命中过敏原。

表中“部分为”“视配方”的项目本身就不能成为硬白名单。

**必须改成字段级证据裁决：**

1. 例外只取消同一字段中的字面子串命中，例如仅取消菜名中的“鱼”；
2. 明确食材命中永远优先，不能被菜名例外覆盖；
3. “部分为”“视配方”的复合菜名进入 `MODEL_ONLY`，不能进入硬例外；
4. 每条例外必须关联 `allergenKey + matchWord + sourceField + exceptionPhrase`，不能只有“组 + 词”；
5. 增加“菜名例外 + 配料真含过敏原”的负例测试。

当前词表还会产生两个未覆盖的确定性问题：

- `FISH` 的“鱼”会把鱿鱼、章鱼类名称误判为鱼；在 `MOLLUSK` 尚未落地时尤其明显；
- `SOY` 的“豆腐”会命中日本豆腐、杏仁豆腐、鱼豆腐，但这些名称不能保证含大豆。

这些复合名称需要逐条归为“明确制品、条件例外或 `MODEL_ONLY`”，不能只给 `FISH` 建例外表而遗漏 `SOY`。

### P0-4 过敏证据覆盖扫描会漏掉弱阳性，也可能漏掉表格行

开发方案规定 `BORDERLINE`（弱阳性、可疑、临界）与 `POSITIVE` 一样进入过敏提醒和菜品拦截；但草案 §9 的 `POSITIVE_MARKS` 只有：

```text
阳性  (+)  ＋  强阳性
```

缺少：

```text
弱阳性  可疑  临界  ±  (+/-)  (±)
```

结果是：模型恰好漏掉唯一“弱阳性”时，覆盖检查可能不触发 `ALLERGEN_SUSPECT_MISS`，模块四仍可能输出。

还有一个结构性问题：当前算法要求**同一个 segment 同时含章节词和阳性标记**。实际表格按逻辑行切分后，章节标题可能在单独 segment 中，数据行只写“鸡蛋白 f1｜阳性”，并不包含“过敏原/IgE/致敏原”等章节词。这种常见版式不会被扫描到。

**修正要求：**

- 将 `POSITIVE_MARKS` 改名为 `ADMITTED_RESULT_MARKS`，覆盖 `POSITIVE + BORDERLINE` 的全部归一化写法；
- 对 `+` 号数量、全半角、括号和大小写统一规范化；
- 解析阶段给逻辑行携带 `sectionContext`，覆盖扫描使用“所属章节 + 本行结果”，不要要求两个词出现在同一字符串；
- 补充“30 项中唯一弱阳性被漏抽”和“标题、数据分属不同 segment”的回归测试。

### P0-5 标准名规则写明了，但草案数据仍违反自身规则

草案 §7.1 规定常量必须写别名表右侧标准名，但 §4.9 仍写：

```text
POTASSIUM 强推荐来源：土豆
```

标准名却是“马铃薯”。这正是 §7.1 用来说明 bug 的原始反例，正文尚未真正修复。

豆腐也存在同类问题：

- `PROTEIN` 以及多项饮食规则写的是泛化“豆腐”；
- 输入中的老豆腐、石膏豆腐会规范化为“北豆腐”；
- 嫩豆腐、内酯豆腐会规范化为“南豆腐”；
- 在精确交集规则下，它们不会命中常量中的“豆腐”。

如果蛋白质规则确实希望两类豆腐都可触发，应显式列出“豆腐、北豆腐、南豆腐”，或建立**仅供该规则使用**的类别成员关系；不能为了钙规则禁止所有营养等价，再让蛋白质匹配静默漏掉。

另有大小写问题：当前 CSV 的匹配词是 `xo酱`，展示名和常见菜名是 `XO酱`。现有 NFKC 规范化不等于 ASCII 大小写折叠，必须明确 matcher 是否执行 `toLowerCase(Locale.ROOT)`，并加入测试。

**应增加构建期校验：**每个精确/别名匹配常量经过规范化后必须等于自身；任何别名左值出现在正式规则中都构建失败。

### P0-6 “北豆腐”不能作为“含钙凝固剂豆腐”的可靠代理

草案已认识到豆腐钙含量取决于凝固剂，但仍把“石膏豆腐 / 北豆腐”并列为可触发来源，并把“老豆腐、北豆腐、石膏豆腐”统一到“北豆腐”。这仍然把产品形态与凝固剂类型混为一谈。

NIH ODS 明确指出，列出的高钙豆腐指使用钙盐加工的豆腐，使用其他盐加工的豆腐并不提供同等显著的钙量。[NIH ODS Calcium — Health Professional Fact Sheet](https://ods.od.nih.gov/factsheets/calcium-HealthProfessional/)

食堂的“北豆腐”字段通常没有凝固剂信息，因此不能可靠推断使用了硫酸钙。

**修正建议：**

- `石膏豆腐`、明确标注“硫酸钙/钙盐凝固”的豆腐：可触发；
- `北豆腐`、`老豆腐`、泛化“豆腐”：仅展示或 `MODEL_ONLY`，不做 Java 正向交集；
- 不得再把“石膏豆腐”规范化为会丢失凝固剂信息的“北豆腐”；
- 若菜品源未来提供营养成分或凝固剂字段，再恢复自动触发。

### P0-7 `LOW_PURINE` 不应由豆腐、豆干触发正向推荐

草案 §5.4 当前把“豆腐、豆干（适量）”放在 `recommendFoods`。国家卫健委公开的相关材料总结现有口径为：对豆制品（如豆腐）**不推荐也不限制**；材料同时认可肉类及高嘌呤植物性食物煮后弃汤可降低嘌呤。[国家卫健委相关标准编制说明](https://www.nhc.gov.cn/cms-search/downFiles/95b495111e564d0ea701da26359ac814.pdf)

因此“可适量食用”不等于“适合用来证明一道菜明确符合低嘌呤要求”。当前写法会把豆腐主料菜直接打为 `RECOMMEND`，证据方向过强。

**修正要求：**

- 豆腐、豆干改为 `DISPLAY_ONLY/NEUTRAL`，不触发 `RECOMMEND`；
- “焯水弃汤”只能作为降低嘌呤的做法提示，不能把本应拒绝的高嘌呤食材翻转为推荐；
- 同步删除 Prompt 中“紫菜嘌呤高，因此固定 REJECT”的旧示例；
- 正向推荐应优先使用指南明确鼓励或低风险、且仅凭当前数据可判断的食物。

### P0-8 高危矩阵的匹配范围和孤立规则仍未定义

当前草案没有明确 `BLOCKED_DIRECTIONS` 和 `MANUAL_REVIEW_PATTERNS` 检查：

- 只检查该条建议的 `conclusionText`；
- 检查同一 segment；
- 检查整个报告的全部可信内容。

这会直接改变结果。例如肾病可能写在报告前文，而“建议补钾”在另一段；如果只查建议原文，`POTASSIUM` 仍会通过。反过来，如果无边界扫描整份报告，“儿童”“流质”等偶然文字又可能把所有建议转为 `OTHER`。

此外，§6.3 声称“低钾血症”已补入 `MANUAL_REVIEW_PATTERNS` 或 `BLOCKED_DIRECTIONS`，但 §6.1 和 §6.2 都没有它，是一条无动作的孤立模式。`CKD` 的 ASCII 大小写处理也没有说明。

**修正要求：**

1. 明确三类输入：当前建议文本、同一临床建议段、经过准入验证的全局患者上下文；
2. 每条 pattern 增加 `scope` 和具体 `action`；
3. 为“肾病在前文、补钾在后文”定义产品允许的安全行为；
4. 明确“低钾血症”的动作；
5. ASCII 医学缩写统一大小写后再匹配；
6. 在无法获得用药史的前提下，`POTASSIUM` 是否退出自动推荐仍应保持上线阻塞。

## 3. P1：医务定稿或联调前应修正

### P1-1 铁摄入量中的动物肝脏频率偏高，必须重新给出处

草案写“动物肝脏每周 1～2 次，每次约 50g”，相当于每月约 4～8 次。国家卫健委公开解读《中国居民膳食指南（2022）》时给出的口径是动物内脏不宜多吃，约每月 2～3 次。[国家卫生健康委 2024-11-14 新闻发布会](https://www.nhc.gov.cn/xcs/c100122/202411/f63a9692d1294dd19c595dce73404417.shtml)

应由医务人员按本产品适用人群重新确定频率与单次量；在具体来源未填入前，不应保留“每周 1～2 次”作为可上线文案。

### P1-2 钙的奶量应写成“奶及奶制品等量”，并复核 300 ml 上限

草案只写“牛奶或酸奶每天约 300ml”。国家卫健委公开口径是一般成年人每天摄入 300～500 ml 液态奶或相当量奶制品。[国家卫生健康委 2024-10-22 新闻发布会](https://www.nhc.gov.cn/xcs/c100122/202410/23f695c3e6b0442281701ba1426430ff.shtml)

建议改为经医务确认的“300～500 ml 液态奶或相当量奶制品”，并说明奶酪等不能直接按毫升相加；如果产品选择更保守的 300 ml，也应在 `sourceReference` 说明依据和适用人群。

### P1-3 蛋白质 1.0～1.2 g/kg 缺少年龄边界

国家卫健委公开说明区分为健康成人约 1.0 g/kg，老年人可增加至约 1.2 g/kg，而不是所有“一般成人”统一使用 1.0～1.2 g/kg。[国务院联防联控机制 2023-01-16 发布会](https://www.nhc.gov.cn/xcs/c100122/202301/27ab1a369157404aaf35a2d4cb8823da.shtml)

建议拆成一般成人和老年人两个适用人群，或只保留 1.0 g/kg 的一般成人口径；同时继续保留 CKD 分期、透析状态个体化处理。

### P1-4 维生素 D 的食物清单与用量依据不够精确

NIH ODS 将富脂鱼类中的鳟鱼、鲑鱼、金枪鱼、鲭鱼列为较好天然来源；蛋黄只含少量，蘑菇含量取决于紫外处理。当前草案中的“鲈鱼”并非该资料列出的代表性高来源，“深海鱼”也不是可稳定映射到营养含量的类别。[NIH ODS Vitamin D — Health Professional Fact Sheet](https://ods.od.nih.gov/factsheets/VitaminD-HealthProfessional/)

建议：

- 用“富脂鱼类”作为展示概念，但机器规则列出经审核的具体鱼种；
- 蛋黄改为仅展示或较弱证据，不单独触发强推荐；
- “每周两次鱼”可作为平衡膳食频次，不应被表述成纠正维生素 D 缺乏的剂量；
- 保留“食物通常不足以纠正已确诊缺乏”的说明。

### P1-5 多个饮食维度仍会在信息不足时产生过强的正向推荐

除草案已列出的 `LOW_SODIUM` 外，还包括：

- `LOW_FAT`：仅有鸡胸肉、鱼或蔬菜，不能证明成菜低脂；烹调油量和做法仍可能很高；
- `LOW_CALORIE`：没有整菜能量和份量，单靠魔芋、冬瓜、鸡胸肉等主料不能证明低能量；
- `LIGHT_DIET`：清蒸、白灼、粥类仍可能高盐、高油或高糖；
- `LOW_CHOLESTEROL`：“使用植物油”不等于用油量合适；
- `LOW_FAT` 把所有“红烧”作为避免做法过宽，红烧本身不能确定脂肪含量。

建议把每项规则逐条标出 `MODEL_ONLY` 或 `recommendationEligible=false`。原则应是：当前菜品字段无法确认时只能 `NEUTRAL`；正向推荐需要比拒绝更完整的证据。

### P1-6 内容条数与既有“3～8 种”合同不一致

README 规定每项营养推荐食材 3～8 种，但：

- `PROTEIN` 有 10 种强推荐来源；
- `IRON` 若强推荐和仅展示在同一卡片合并呈现，共 9 种。

需要明确“3～8”是每个分层字段限制，还是整张卡片展示总数限制，并让 registry 生成器校验。若产品不再需要该限制，应同步修改 README 和前端展示约束。

### P1-7 `evidenceLevel` 与 `matchMode` 缺少合法组合约束

草案文字隐含：

- `DIRECT/LIKELY` 可进入 Java；
- `POSSIBLE` 必须 `MODEL_ONLY`。

但数据结构允许写出 `POSSIBLE + EXACT`、`DIRECT + MODEL_ONLY` 等组合。后者未必错误，前者却违反安全规则。

应在 registry Schema/生成器中定义合法矩阵，并明确 `LIKELY` 做硬拒绝所需的最低医务证据。`bucket=hidden` 不应被误解为证据强度低；它只描述展示分组。

### P1-8 当前 CSV 注释与项目最高优先级规则冲突

`allergen_display_split.csv` 注释写“不得增删 matchWord 行”，而 `AGENTS.md` 明确规定该 CSV 是可扩充的参考基线，增删词条属于需评审记录的安全变更，并非永久禁止。

迁移到新 registry 时应删除这条绝对禁止注释，改为：

> 增删 matchWord 必须附评审记录、测试与 contentVersion 变更，禁止绕过 registry 在 Java 中直接加词。

### P1-9 医学治理字段仍是空结构，无法形成审核闭环

草案已提出 `sourceReference/reviewer/reviewDate/...`，但正文每一行都未实际填写，§11 只有资料名称且标为“待核实”，审核表也全空。

建议不要等审核时再临时补 Java 注解。应先确定伴生元数据格式，并让每条规则通过稳定 `ruleId` 关联：

```text
sourceReference = 发布机构 + 文档全名 + 年版 + 章节/页码 + URL
reviewStatus     = 只有 REVIEWED 才进入生产生成物
reviewer         = 姓名或内部工号
reviewDate       = ISO 日期
nextReviewDate   = ISO 日期
```

`DRAFT` 和 `REJECTED` 行是否参与 Prompt、展示和测试也要明确；最安全的规则是二者均不进入生产生成物。

## 4. P2：一致性与可维护性问题

### P2-1 `matchWord` 注释“宽松”与 `EXACT` 名称矛盾

需要明确 `EXACT` 是整字符串相等、标准分词后的 token 相等，还是当前的无边界子串匹配。中文菜名的结果差异很大。建议枚举直接命名为 `SUBSTRING`、`CANONICAL_EXACT` 等能体现真实语义的名称。

### P2-2 例外词典“上限 30 条”缺少工程或安全依据

词条数量不应成为是否安全的判据。可以把“例外过多”设为人工复核指标，但不应设置会阻止必要安全例外进入的固定上限。

### P2-3 `foodBorne` 更适合组级元数据

同一 `allergenKey` 下每个词重复保存 `foodBorne` 容易出现行间不一致。建议建立 `allergen_group` 与 `allergen_word` 两个逻辑表，组级保存展示名、是否食入性、排序；词级只保存匹配与证据属性。若坚持单表，生成器必须验证同组值完全一致。

### P2-4 `contentVersion` 与 `retagRequired` 的关系不清楚

当前又要求任何内容变化 bump 全局 `contentVersion`，又给每条内容设置 `retagRequired`。如果全局版本参与 `tagPolicyVersion`，即使只改展示文案、`retagRequired=false`，仍会触发全部 20 维度重打标。

需要二选一：

- 接受所有内容改动都全量重打标，删除容易误导的 `retagRequired`；或
- 拆分 `displayContentVersion` 与 `tagRuleVersion`，只有影响打标的字段进入 `tagPolicyVersion`。

该项属于性能和发布成本问题，不影响医学正确性。

## 7. 可直接写入 CI 的验收清单

- [ ] registry 是枚举、Schema、Prompt 和 Java 常量的唯一机器真源；
- [ ] 生成后仓库无 diff，否则构建失败；
- [ ] 每条规则有唯一稳定 `ruleId`；
- [ ] 生产生成物只包含 `reviewStatus=REVIEWED` 的规则；
- [ ] `POSSIBLE + EXACT` 等非法组合构建失败；
- [ ] 每个标准食材常量规范化后等于自身；
- [ ] 正式规则中不出现别名表左值；
- [ ] ASCII 匹配统一大小写，`xo酱` 能命中 `XO酱`；
- [ ] 菜名例外不能覆盖明确配料命中；
- [ ] 鱿鱼不触发 `FISH` 硬拒绝；
- [ ] 日本豆腐、杏仁豆腐、鱼豆腐不会仅因名称被 `SOY` 硬拒绝；
- [ ] 唯一弱阳性漏抽会触发 `ALLERGEN_SUSPECT_MISS`；
- [ ] 章节标题与阳性数据行分属不同 segment 时仍能完成覆盖检查；
- [ ] `LOW_PURINE` 的豆腐、豆干不能单独产生 `RECOMMEND`；
- [ ] 未知盐、油、糖、能量或份量时，相应维度不能产生无依据的 `RECOMMEND`；
- [ ] 所有表格条数、标准名、类别成员、引用和审核状态均可由程序校验；
- [ ] 审核记录未填满时，模块三和模块四的生产开关保持关闭。

## 8. 最终判断

当前草案适合作为“第三轮数据设计和医务评审输入”，但还不是可直接编码的常量规格。完成 P0-1 至 P0-8 后，工程团队才可以稳定实现 registry、生成器和匹配器；完成所有医学 P1 与审核记录后，才适合生成生产常量。
