## 1. 常量类的结构语义



### 1.1 为什么拆成这些字段

上一版把展示内容、Java 硬判定和医学建议混在同一张表里，
医务审一句「补铁推荐吃菠菜」的文案时，实际同时批准了
「菠菜是主料的菜自动推荐给缺铁用户」这条匹配规则——两者证据强度完全不同。

拆开之后，**「产生什么判定」由字段本身表达，不靠额外的标记列**：

```java
NutritionRule.recommendableFoodList   参与主料交集 → 可触发推荐
NutritionRule.displayOnlyFoodList     只出现在模块三 → 永不触发推荐
DietRequirementRule.avoidFoodList     产生 REJECT
DietRequirementRule.displayOnlyFoodList  只展示（本类【没有】可推荐字段）
```

医务可以把菠菜写进 `displayOnlyFoodList`（科普有价值），同时拒绝让它触发自动推荐
——这比在一张表里加一个 `recommendationEligible` 布尔列更难写错：
**字段放错位置会编译报错，布尔值填错不会。**

`foodBorne` 在 `AllergenGroup` 上只存一次，126 个词条不再各自重复，天然不会不一致。

### 1.2 `AllergenWord`

| 字段 | 取值 | 说明 |
|---|---|---|
| `bucket` | `avoid` / `hidden` | **只描述展示分组，不代表证据强度** |
| `evidenceLevel` | `DIRECT` / `LIKELY` / `POSSIBLE` | 决定是否进 Java 硬匹配 |
| `matchMode` | `SUBSTRING` / `MODEL_ONLY` | 见 §1.4 |

```
DIRECT   该词本身即该过敏原或其直接制品（虾仁、芝麻、牛肉）      → Java 硬匹配
LIKELY   绝大多数配方含有，但存在例外（虾丸、蛋挞）              → Java 硬匹配
POSSIBLE 配方差异大，名称不能保证（XO酱、海鲜酱、蟹棒、奶油）     → 只进 LLM-B 提示词
```

**合法组合矩阵，单元测试必须强制：**

| evidenceLevel | 允许的 matchMode |
|---|---|
| `DIRECT` | `SUBSTRING` |
| `LIKELY` | `SUBSTRING` |
| `POSSIBLE` | **只能 `MODEL_ONLY`** |

`POSSIBLE + SUBSTRING` 是非法组合，出现即构建失败——它会把「配方不保证」的词
做成硬拒绝，正是 §4.1 要避免的误拦。

### 1.3 `AllergenExceptions` —— 例外只作用于菜名

**`sourceField` 当前只允许 `DISH_NAME`。**

```
例外命中 → 只取消【菜名】里那个字面子串的命中
食材表里的明确命中 → 永远优先，例外不可覆盖
```

具体说：「鱼香肉丝」的菜名例外只取消菜名中「鱼」的命中；
如果这道菜的配料表里确实另有**鱼露**，`FISH` 仍然 `REJECT`。

**「部分为」「视配方」这类条件性复合菜名不进例外表**，
它们归 `POSSIBLE + MODEL_ONLY`——蟹黄豆腐可能用咸蛋黄也可能真含蟹黄，
做成硬白名单就是漏拦。

### 1.4 `matchMode` 的精确语义

上一版用 `EXACT` 命名，但注释又说 `matchWord` 是「宽松匹配」，自相矛盾。
中文菜名下两者的结果差别很大，本版改为三个能自解释的名字：

| matchMode | 语义 | 用在哪 |
|---|---|---|
| `SUBSTRING` | 规范化后**子串包含** | 过敏 Layer 1（宁可过杀） |
| `CANONICAL_EXACT` | 规范化后**整串相等** | 营养维度的主料交集（§9.2） |
| `MODEL_ONLY` | **不做任何 Java 匹配**，只作为线索进提示词 | `POSSIBLE` 词、无法从食材证明的饮食维度 |
| `NONE` | 纯文案，不参与匹配 | 摄入量、搭配贴士、烹饪与行为建议 |

**规范化包含 ASCII 大小写折叠**（`toLowerCase(Locale.ROOT)`），
所以词表里的 `xo酱` 能命中菜名里的 `XO酱`。NFKC 不做大小写折叠，必须单独执行，
并有对应单测。

### 1.5 `NutritionContents` 与 `DietRequirementContents`

```java
NutritionRule {
    recommendableFoodList   // 参与 §9.2 主料交集，CANONICAL_EXACT 匹配
    displayOnlyFoodList     // 只展示
    intakeNoteList / pairingTipList / contraindication
}

DietRequirementRule {
    displayOnlyFoodList     // 正向食材，只展示 —— 本类没有可推荐字段
    avoidFoodList           // 产生 REJECT
    avoidDishPatternList    // 产生 REJECT
    cookingTipList / behaviorTipList / contraindication
}
```

**`DietRequirementRule` 结构上就没有「可推荐」这个字段**，
所以饮食注意维度不可能产生推荐——这不是靠约定，是类型保证的。
LLM-B 的 `verdict` 枚举因此只能是 `REJECT`。

食材、菜式、烹饪方式、用餐行为分成不同字段，是因为它们不是一回事
——混在一个数组里，程序和模型都会把「蒸蛋」当成一种食材。

### 1.6 没有 `CATEGORY` 匹配模式

上一版提过 `CATEGORY`（「绿叶蔬菜」「深海鱼」这类），本版**不做**。

理由：类别成员没有真源。「绿叶蔬菜」包含哪些标准食材、谁来维护这张表，都没有定义；
交给模型展开的话它就不是确定性匹配，不该叫 `CATEGORY`。

因此类别性表述一律走 `MODEL_ONLY`。将来若要启用，必须先建类别成员常量并同样进审核流程。

## 2. 审核元数据与产出规则

### 2.1 审核元数据放哪

**运行时需要的只有 `reviewStatus`**，它是每个常量对象的一个字段：

```java
AllergenWord.of("虾", "虾", Bucket.AVOID, EvidenceLevel.DIRECT,
                MatchMode.SUBSTRING, ReviewStatus.DRAFT)
```

**审核台账（来源、审核人、日期、结论、拒绝理由）不进 Java**
——206 条营养规则各带 5 个字符串会让常量类没法读。
它们记录在本文档 §8 的审核记录表里，靠**类名 + 常量名 + 词**定位，
例如「`AllergenGroups.SHRIMP_CRAB` 的 `海鲜酱`」。

> 上一版用 CSV 时给每行发过 `ruleId`。现在真源是 Java，
> 常量的**位置本身就是标识**（哪个类、哪个字段、第几个词），不需要再造一套 ID。
> 台账里写 `AllergenGroups.SHRIMP_CRAB / 海鲜酱` 比写 `AW0013` 更好查。

### 2.2 审核状态影响什么、不影响什么

「只让 `REVIEWED` 的内容存在」这条是危险的：
审核到一半会生成「半个过敏原维度」——`SHRIMP_CRAB` 审了 5 个词、剩下 5 个还是 `DRAFT`，
线上就会用一个残缺的词表做 Layer 1，**看起来在防护，实际漏拦**。

**因此拆成三层：**

| 层 | 受审核状态影响吗 | 说明 |
|---|---|---|
| **枚举身份**（`AllergenKey` / `NutritionKey` / `DietRequirementKey`、Schema enum、Prompt 枚举表） | **否** | 枚举常量始终存在。身份稳定，接口契约不会因审核进度抖动 |
| **生效规则**（Layer 1 词表、营养交集集合、LLM-B 提示词注入的内容） | **是** | 只用 `REVIEWED` 的行 |
| **发布激活** | **按快照原子生效** | 见下 |

**发布激活按整个常量类原子启用**，不是审完一条就改一条：

```
发布前置条件：
  ① 该类的【全部常量】都已裁决（REVIEWED 或 REJECTED），没有 DRAFT 残留
  ② 发布清单（哪些生效、哪些被拒、拒的理由）经审核通过
  ③ 通过后一次性 bump TagRuleVersion.VALUE 并触发全量重打标
```

代码层面就是一次 PR 把该类的 `ReviewStatus.DRAFT` 全部改掉，评审时能看到完整 diff。

**完成标准是「全部行已裁决 + 发布清单通过」，不是「全部改成 REVIEWED」**
——被拒的规则也是一个明确结论，不是未完成。

`REJECTED` 的常量**保留在类里但不生效**，并且**必须出现在负向回归测试中**：
「这个词曾被评估过并明确拒绝」是有价值的测试用例，
直接删掉会让它有机会在下一次悄悄被加回来。

## 3. 版本与重打标

上一版要求任何内容变化都 bump 全局 `tagRuleVersion`，同时又给每条规则设
`retagRequired`——两者矛盾：全局版本进了打标哈希，
那么只改一句展示文案也会触发全部 22 个维度重打标。

**本版只保留一个版本号，并把展示类内容排除在外：**

```java
展示类内容              INTAKE_NOTE / PAIRING_TIP / COOKING_TIP / BEHAVIOR_TIP
                        以及 DISPLAY_ONLY 行改动时，不 bump 任何版本号
                        → 不进 tagHash，不触发重打标

tagRuleVersion          影响打标的内容改动时 bump：
                        AllergenGroups / AllergenExceptions 的任何词条、
                        NutritionContents.recommendableFoodList、
                        DietRequirementContents 的 avoidFoodList / avoidDishPatternList
                        → 进 tagHash，触发全量重打标
```

```
tagHash = sha256(tagRuleVersion + "|" + promptVersion + "|" + modelVersion + "|"
                 + normalize(菜名) + "|" + 食材串)
```

> **2026-08-28：`DisplayContentVersion` 常量已删除。** 拆分决策本身不变——展示类内容改动
> 仍然不得 bump `tagRuleVersion`——但那个常量没有任何消费点：不进 `tagHash`，
> 分析结果按 `result:{taskId}` 存、两小时 TTL，本来就活不过一次改文案的发布，
> 不需要版本参与失效。留着只是一条写成 Java 常量的文档，改它没有任何运行时后果。

> **2026-08-24：不存在 `tagPolicyVersion`。** 上一版把「规则版本」单独做成一个哈希列，
> 与 `dishHash` 并列进唯一键。现已合并为一个 `tagHash`——判定方与被判定方拼进同一个哈希，
> 唯一键是 `(dish_id, tag_hash, enum_key)` 三列。开发方案 §9.5。

`retagRequired` 这一列删除——它的作用已由「该行的 `verdictEffect` 是不是 `DISPLAY_ONLY`」
自动推导出来，多一个可以填错的字段没有价值。

## 4. 2026-08-27 严格裁决 —— 会改变拦截或推荐行为

本章原“待裁决”事项已按证据强度和安全不对称原则裁决。逐条依据见
`内容常量证据审核台账V1.md`；本章只保留会影响产品行为的摘要。

### 4.0 前提变更：菜品食材表【不含调味料】（2026-08-25 确认）

食堂的 `ct_dish_ingredient` 只记主料与配料，**油、盐、糖、酱油、醋、料酒、蚝油、香油、
豆瓣酱、沙拉酱、XO酱、鸡精、淀粉一概不入表**（设计方案 §8.1.1）。

这条事实改变了本章几乎每一项裁决的权重：

```
调味料类词条（蚝油、香油、XO酱、海鲜酱、豆瓣酱…）
    → 在食材名上【永远匹配不到】，它们唯一的作用是【命中菜名】
    → 词条本身没有失效，但它的覆盖面从"食材 + 菜名"缩到了"菜名"
    → 「蚝油生菜」还拦得住；「红烧肉里的酱油」「凉拌黄瓜里的香油」拦不住
```

**Java 词表这一层因此从"双保险"退化成"菜名保险"**，调味料带来的过敏原主要落到
LLM-B 的三态安全判定上（设计方案 §8.4）：有明确菜名/配方证据才可 `REJECT`，否则为
`UNKNOWN`，不得用常识补出实际配方。两个直接后果：

1. **`MOLLUSK` 与 `SESAME` 已补入正式食入性过敏原组**；明确菜名可命中，模糊别名仅作模型线索。
2. **`WHEAT` 与 `SOY` 均收录明确的「酱油」词；`WHEAT` 另收录「豉油」**。
   但「红烧、酱爆、卤」只说明做法，不能证明具体配方，明确排除在硬词表之外。

> **词表里的调味料词条不要因为"食材表里用不上"就删掉。** 它们要靠菜名命中，
> 而菜名里出现调味料是很常见的（蚝油生菜、麻酱拌面、XO酱炒饭）。

| 词 | 现属组 | 问题 | 已做的处理 |
|---|---|---|---|
| **海鲜酱** | `SHRIMP_CRAB` hidden | 传统 hoisin 是**发酵豆酱，可能根本不含海鲜**，真实风险是大豆与小麦 | 在 `SHRIMP_CRAB` 中 `REJECTED`；在 `SOY` / `WHEAT` 中以 `POSSIBLE + MODEL_ONLY` 保留 |
| **蟹柳 / 蟹棒** | `SHRIMP_CRAB` hidden | 市售仿蟹肉棒主料通常是**鱼糜**，名称不能证明含真蟹 | 在 `SHRIMP_CRAB` 中 `REJECTED`；在 `FISH` 中以 `POSSIBLE + MODEL_ONLY` 保留 |
| **XO酱** | `SHRIMP_CRAB`、`MOLLUSK` hidden | 配方差异大，不保证同时含干贝与虾米 | 两组均只作 `POSSIBLE + MODEL_ONLY` 线索，不做 Java 硬拒绝 |

前两条若属实，当前词表**同时存在误拦和漏标**：拿海鲜酱拦虾蟹过敏者是误拦，
真正大豆过敏的人不会被它拦住；鱼过敏者吃蟹棒则完全没有防护。

### 4.2 过敏原组裁决

> **本次契约升级后的固定值是：过敏原枚举 18（13 食入 + 5 非食物）、LLM-B 维度 22、
> 正式枚举 36。** Schema、Prompt、Java 容量、Prompt 版本和 `tagRuleVersion` 已同步；部署后必须
> 全量重打标并通知前端与模型侧。

| 组 | 优先级 | 备注 |
|---|---|---|
| `MOLLUSK` 软体动物 | **纳入** | 直接物种名和蚝油/蚝汁可拦截；`XO酱` 仅 `MODEL_ONLY`。`FISH` 的鱿鱼/章鱼/墨鱼菜名例外继续保留，避免泛词「鱼」先误杀 |
| `SESAME` 芝麻 | **纳入** | 芝麻、芝麻酱、芝麻油硬匹配；「麻酱、香油、麻油」存在地区和复配歧义，仅 `MODEL_ONLY` |
| `PINEAPPLE` 菠萝 | **本次不纳入** | 不属于此次已确认的上线缺口，且「菠萝油」存在明确非菠萝语义；需要真实报告命中数据后另立变更 |
| `PORK` / `CHICKEN` | **本次不纳入** | 未形成可审计且误杀可控的词表，不能借本次扩容顺带加入 |

### 4.3 高风险词裁决

| 组 | 词 | 风险 |
|---|---|---|
| `SOY` | **酱油** | `LIKELY + SUBSTRING`；菜名明确出现酱油时从严拦截。此处是产品安全策略，不宣称所有大豆过敏者都会对发酵酱油反应 |
| `WHEAT` | **酱油 / 豉油** | `LIKELY + SUBSTRING`；国标酿造酱油原料范围支持其作为高可信线索，但最终仍以实际配方/标签为准 |
| `WHEAT` | **红烧 / 酱爆 / 卤** | **不收录。** 做法不能证明用了哪种酱油或是否使用酱油；LLM-B 无菜名/食材直接证据时必须 `UNKNOWN`，不能凭常识硬拒绝 |
| `EGG` | **鸭蛋 / 鹅蛋 / 鹌鹑蛋** | 纳入 `POSSIBLE + MODEL_ONLY`，提示模型核对具体个体过敏范围，不做 Java 硬拒绝 |

其余漏词（`EGG` 蒸蛋炒蛋蛋花、`SOY` 豆干千张素鸡、`WHEAT` 馒头包子面筋裹粉、
`NUTS` 松子巴旦木碧根果、`MILK` 奶粉乳清蛋白酪蛋白、`PEANUT` 花生碎花生粉）
风险较低，但仍须逐条确认后再写入常量类。

### 4.4 高风险营养项裁决

| 项 | 问题 |
|---|---|
| `POTASSIUM` | 保留模块三的条件性展示；`recommendableFoodList` 继续为空。肾功能、血钾和用药史不完整时，系统不得自动推荐高钾菜 |
| `PROTEIN` | 保留一般人群展示与主料交集，但禁忌文案明确肾病、肝病等场景须个体化；与低蛋白医嘱冲突时由高风险规则阻断 |
| 蛋黄 | 不列入 `LOW_CHOLESTEROL` 的绝对避免项；以整体膳食、饱和脂肪及个体医嘱为准，不把一般人群建议改写成疾病治疗处方 |

### 4.5 摄入量与频次裁决

| 项 | 草案原写 | 复审指出 |
|---|---|---|
| 动物肝脏 | 每周 1~2 次 | 卫健委解读口径为动物内脏不宜多吃、约每月 2~3 次，**原写法偏高** |
| 奶量 | 每天约 300ml | 一般成人 300~500ml 液态奶或相当量奶制品；奶酪不能按毫升相加 |
| 蛋白质 | 一般成人 1.0~1.2 g/kg | 应拆分：健康成人约 1.0，老年人可增至约 1.2 |
| 维生素D 鱼种 | 三文鱼、鲈鱼、沙丁鱼 | 已改为三文鱼、鳟鱼、金枪鱼、鲭鱼；「鲈鱼」非代表性高来源 |

## 6. `RadicalNormalizeMap` 与工程侧常量

`RadicalNormalizeMap` **不在 `constants` 包**，它是纯工程映射，但同样标 🟡：

```
只作用于 normalizedText，绝不作用于 rawText
只能基于真实「污染字符 → 预期字符」样本加入，不得按 Unicode 块批量推导
每条映射保留一个回归样本（原始 PDF 片段 + 期望结果）
```

上一版按 Unicode 块整理的 18 条**降级为待验证候选**，拿到真实样本前不入代码。

> NFKC 已处理康熙部首区（U+2F00–U+2FD5）；CJK 部首补充区（U+2E80–U+2EFF）
> 无兼容分解，需手工映射。

其余工程侧常量（`DisclaimerConstants`、`EmptyStateConstants`）见开发方案 §10，
不需要医学审核。

> **三张语义词表已移出生产代码**（2026-08-25，设计方案 §4.4-③）：
> `ConclusionLabelWords`、`NormalStatementWords`、`AllergenSectionWords`
> 原本用于在线比对告警（`statusConflictCount` 等三个计数），现已整体下线
> ——**只用于观察的东西不该跑在每一次用户请求里**，而且它长得和"Java 在判断医疗语义"
> 一模一样，留在生产里迟早被改回覆写。三者现在只存在于**离线评测集**（设计方案 §11-18），
> 不打包、不发版、不需要医学审核；但评测集里的 `NormalStatementWords` 同样**不含「阴性」**
> （§4.3-6「阴性 ≠ 正常」与它跑在哪里无关）。
>
> **`SeasoningWords` 整个删除**：食材表本来就不含调味料（§4.0），
> 原本用于「主料推导时排除调味料」的那一步是空操作（设计方案 §8.8）。

**`ADMITTED_RESULT_MARKS`（原 `POSITIVE_MARKS`）已扩充**，覆盖 `POSITIVE + BORDERLINE`：

```
阳性  强阳性  弱阳性  可疑  临界  阳
(+)  （+）  ＋  +  ++  +++  ±  ＋/－  (±)  (+/-)
```

上一版只有「阳性/(+)/＋/强阳性」四个，**模型漏掉唯一一条弱阳性时覆盖检查不触发**。
匹配前统一做全半角、括号、`+` 号数量的归一化。

## 7. 契约测试与 CI

**没有生成器。** 常量类是手写的真源，Schema 与 Prompt 是独立文件。
两者之间靠**契约测试**防漂移——前两轮评审抓到的 12/21 vs 11/20 不一致，
就是因为 Java、Schema、Prompt 各写各的，没人拦。

```java
@Test
void schema枚举必须与Java枚举一致() {
    Set<String> fromJava = enumNames(AllergenKey.class);            // 含 OTHER
    Set<String> fromSchema = readEnum("schema/extraction_output.schema.json",
                                      "$defs.allergenKey.enum");
    assertEquals(fromJava, fromSchema);   // 对不上就构建失败
}
```

**必须由测试覆盖的一致性：**

```
□ AllergenKey        ↔ llm_a schema $defs.allergenKey.enum
□ NutritionKey       ↔ llm_a schema $defs.nutritionKey.enum
□ DietRequirementKey ↔ llm_a schema $defs.dietRequirementKey.enum
□ 食入性组 ∪ 饮食注意 ↔ dish_tag schema properties.enumKey.enum（当前 22）
□ 上述四组          ↔ prompt/extraction.md 的枚举表章节
□ LLM-B 维度计数     ↔ prompt/dish_tag.md 的描述（当前 22）
□ DietRequirementRule 无可推荐字段 ⇒ llm_b schema 的 verdict enum 只有 REJECT
```

**其余必测规则：**

```
□ POSSIBLE 的词条 matchMode 必须是 MODEL_ONLY（非法组合即失败）
□ 同组内 avoid ∩ hidden = ∅
□ 每个 CANONICAL_EXACT 常量规范化后等于自身
□ 常量中不出现别名表左值（土豆 / 老豆腐 / 西蓝花）
□ ASCII 大小写折叠生效：xo酱 能命中 XO酱
□ 发布候选四个内容类无 DRAFT；如未来出现全 DRAFT 快照，枚举仍完整但规则不注入
□ 存在 DRAFT 残留时拒绝发布
□ REJECTED 的词出现在负向回归测试夹具中
□ DISPLAY_ONLY 的食材不注入 LLM-B 提示词、不参与营养交集
□ 菜名例外不能覆盖明确配料命中
□ 鱿鱼不触发 FISH 硬拒绝；日本豆腐 / 杏仁豆腐 / 鱼豆腐 不被 SOY 硬拒绝
□ 唯一弱阳性被漏抽时触发 ALLERGEN_SUSPECT_MISS
□ LOW_PURINE 的豆腐豆干不产生 RECOMMEND
□ constants 包有 diff 但 TagRuleVersion.VALUE 未变 → 构建失败
```

最后一条最关键：**忘记 bump 版本号的后果是静默的**
——菜和食材都没变，凌晨预热的 diff 会认为标签已存在而跳过，新规则永远不生效，
不报错也不告警。
