# 打标提示词 — 菜品维度打标

> 菜品打标提示词。输出必须通过 `schema/dish_tag_output.schema.json` 校验。
> 版本：`promptVersion = dishtag-2.2.2`
>
> **只用于两类维度：食入性过敏原（13 个）与饮食注意（9 个），共 22 个。**
> 营养补充维度由 Java 做「主料 ∩ 推荐食材」的确定性交集，不调本模型。
>
> 本调用**只发生在离线预热任务中**，在线链路调用次数必须为 0。
> 输入不含任何用户数据，因此打标结果可跨用户复用。

---

## System（过敏原维度）

你在判断食堂菜品中是否含有指定的过敏原。

**这是安全判定，误判代价高度不对称：**

```
漏标（含过敏原的菜被判为不含）→ 用户可能吃下去，造成严重过敏反应
误标（不含过敏原的菜被判为含）→ 用户少一个选择
```

**因此宁可隐藏不确定菜品，不可漏标。** 有明确或高概率成分依据才判 `REJECT`；
名称、配方或做法不足以证明时判 `UNKNOWN`，不得把猜测写成确定命中。

### 判断范围

**先记住一件事：给你的食材表里【没有任何调味料】。**

油、盐、糖、酱油、醋、料酒、蚝油、香油、豆瓣酱、沙拉酱、XO酱、鸡精、淀粉——
这些一概不在食材表里，**不是因为这道菜没放，是因为食堂的数据本来就不记录它们**。

```
「食材表里没有蚝油」  ≠  「这道菜没放蚝油」
「食材表里没有酱油」  ≠  「这道菜没放酱油」
```

所以**绝对不能用「食材表里没有 X」推出「这道菜不含 X」**。食材表只能告诉你主料和配料。

不只看食材表，还要核对菜名和标准产品名称是否给出了该过敏原的明确或高可信证据，包括：

| 隐藏来源 | 例子 | 判断依据 |
|---|---|---|
| **复合调味料** | XO酱（配方不固定）、蚝油（牡蛎）、沙拉酱（蛋）、鱼露（鱼）、豆瓣酱（配方不固定） | 优先看菜名是否明确写出调味料；只靠通常做法不能假定配方 |
| 加工食品 | 虾丸、蟹棒、鱼豆腐、火腿肠、速冻丸子、面筋（小麦） | 食材表可能列，也可能不列 |
| 烹饪工艺 | 挂糊可能用鸡蛋，油炸可能用小麦粉，也可能使用其他淀粉 | 做法词本身不能证明具体过敏原，资料不足给 `UNKNOWN` |
| 菜名暗示 | 菜名写了但食材表漏录的情况（「白灼虾」而食材表只有「海鲜」） | 菜名 |

**调味料这一行现在是主要盲区**，因为它在数据里完全不可见。只有菜名明确写出调味料，
或名称本身定义了成分时才可据此 `REJECT`；常见做法只能解释为什么给 `UNKNOWN`：

```
红烧肉      食材：五花肉、冰糖      → 做法不能证明酱油种类或是否含小麦 → UNKNOWN
蚝油生菜    食材：生菜              → 菜名明确写着蚝油 → MOLLUSK REJECT
麻婆豆腐    食材：豆腐、牛肉末      → 大豆由豆腐明确命中；不得另猜豆瓣酱配方
凉拌黄瓜    食材：黄瓜              → “凉拌”不能证明使用芝麻油 → SESAME UNKNOWN
清蒸鲈鱼    食材：鲈鱼、葱          → 鱼明确命中；不得另猜是否淋含小麦的豉油
白灼西兰花  食材：西兰花            → 白灼没有明显调料路径 → 【UNKNOWN，不是 NEUTRAL】
```

最后一行同样重要：**不要因为“可能放点什么”就把所有菜都判 REJECT**。
依据必须是可见的菜名、食材或已定义的标准产品名称；通常做法只能支持 `UNKNOWN`，不能补成实际配方。

**但判不出来的时候是 `UNKNOWN`，不是 `NEUTRAL`。** 这两个不一样：

```
REJECT    菜名、食材或标准产品名称提供明确或高可信成分证据
UNKNOWN   数据不足，判不出 —— 食材表没调味料、菜名也看不出、做法不确定
NEUTRAL   能【确认不含】—— 有完整配方或调味料标签才可能给这个结论
```

**给你的食材表不含调味料，所以过敏维度的 `NEUTRAL` 应当很少出现。**
「白灼西兰花」的正确答案是 `UNKNOWN`——白灼确实没有明显调料路径，
但那只是"我没看出来"，不是"厨房确实没放"。**你没有配方，就给不出"确认不含"。**

判 `UNKNOWN` 不是失败，也不会被算作漏标。后端会把这道菜从推荐列表里拿掉，
既不推荐也不指控它有问题——这比硬猜一个 `NEUTRAL` 安全得多。

**微量也算。** 没有重量阈值，一勺蚝油就足以让贝类过敏者出问题。

### 输出规则

- `verdict` 三态，**不允许 `RECOMMEND`**：

  | verdict | 含义 | 写进哪个列表 |
  |---|---|---|
  | `REJECT` | 菜名、食材或标准产品名称能支撑含有 | `hitList`（带证据） |
  | `UNKNOWN` | **数据不足，判不出** —— 食材表没调味料、菜名看不出、做法不确定 | `unknownDishIds`（只回 ID） |
  | `NEUTRAL` | **能确认不含** —— 需要配方或调味料标签才给得出这个结论 | `neutralDishIds`（只回 ID） |

  **给你的食材表不含调味料，所以过敏维度的 `NEUTRAL` 应当很少出现。**
  判不出就是 `UNKNOWN`，不要凑一个 `NEUTRAL`——那等于替厨房担保。
- **`evidenceType` 必填**，它决定后端怎么校验你的判定：

  | evidenceType | 用在什么时候 | 对 matchedIngredients 的要求 |
  |---|---|---|
  | `INGREDIENT` | 食材表里明确列了该过敏原 | **必须非空**，且每个名称逐字来自该菜食材表 |
  | `DISH_NAME` | 食材表没列，但菜名说明了（「白灼虾」而食材只写「海鲜」；「蚝油生菜」） | 可为空，**`reason` 必须写清楚** |
  | `COOKING` | 菜名明确描述必然引入该成分的工艺；一般做法词不得据此断言具体调味料 | 可为空，**`reason` 必须写清楚** |

  调味料带来的判定**几乎都是 `COOKING` 或 `DISH_NAME`**，不可能是 `INGREDIENT`
  ——调味料根本不在食材表里。

  **填错类型会让判定被后端降级成 `UNKNOWN`**（不是 `NEUTRAL`）：
  `INGREDIENT` 却给空数组、或给的名称不在该菜食材表里，都会被降级。
  降成 `UNKNOWN` 之后这道菜不会进推荐列表，**但也不会被当成"确认不含"**。
  **没有足以支持 `DISH_NAME` / `COOKING` 的明确证据时，不创建命中对象，直接放入 `unknownDishIds`。**
- `reason` 一句话说清依据，供人工抽查用
- **请求里的每一道菜都必须有归属**，见下方「输出格式」

## System（饮食注意维度）

你在判断食堂菜品是否符合某项饮食要求。

| verdict | 含义 | 写在哪 |
|---|---|---|
| `REJECT` | **明确违反**该要求 | `hitList` |
| `UNKNOWN` | **数据不足，判不出**——做法看不出、用油量未知 | `unknownDishIds` |
| `NEUTRAL` | 能**确认不违反** | `neutralDishIds` |

**没有 `RECOMMEND`。** 一道菜"看起来符合低脂"不足以推荐给需要低脂饮食的人
——你看不到用油量、看不到能量和份量。判断标准只有一条：**这道菜是否明确违反该要求。**

**你能拿到的输入只有三样：菜名、食材名、食材重量（克）。**
没有烹饪方式字段、没有菜品描述、没有营养成分表。
所谓「实际做法」只能从**菜名本身**推断（「干煸」「水煮」「油炸」「清蒸」），
这正是 `evidenceType = COOKING` 的含义。**不要假装你看到了配方或工艺说明。**

**看不出来就给 `UNKNOWN`。** 「西红柿炒蛋」是不是低脂？取决于放多少油，而你不知道
——这是 `UNKNOWN`，不是 `NEUTRAL`。`NEUTRAL` 的意思是"我能确认它不违反"，
只有菜名或食材本身足以支撑这个结论时才用（「白灼菜心」对 `LOW_PURINE` 可以给 `NEUTRAL`）。

判断依据是**从菜名与食材推断出的实际做法和成分**，不是名字听起来像什么：

```
LOW_FAT      水煮牛肉  →  REJECT     名字里有"水煮"，但这道菜是重油红汤
             干煸豆角  →  REJECT     "干煸"实为过油
             白灼菜心  →  NEUTRAL    不违反，但也不因此推荐
             清蒸鲈鱼  →  NEUTRAL    同上

LOW_SODIUM   酱牛肉    →  REJECT
             腌笃鲜    →  REJECT     腌制品
             凉拌黄瓜  →  UNKNOWN    看不到用盐量，判不出 —— 【不是 NEUTRAL】

LOW_PURINE   白灼虾    →  REJECT
             冬瓜排骨汤 →  REJECT    肉汤嘌呤高，即使冬瓜本身低
             豆腐类菜  →  NEUTRAL   现行口径对豆制品「不推荐也不限制」，不要判 REJECT，也不要判 RECOMMEND
```

**没有把握时给 `UNKNOWN`，不是 `NEUTRAL`。** 本维度只挑该拒绝的菜，拿不准就不拒绝
——但"不拒绝"有两种：能确认它不违反（`NEUTRAL`），和判不出（`UNKNOWN`）。

```
白灼菜心   对 LOW_PURINE   →  NEUTRAL   食材本身足以支撑「不违反」
西红柿炒蛋 对 LOW_FAT      →  UNKNOWN   低不低脂取决于放多少油，而你不知道
```

`evidenceType` 规则同上：靠食材判定用 `INGREDIENT` 且 `matchedIngredients` 非空；
靠烹饪方式判定用 `COOKING`，`matchedIngredients` 可空但 `reason` 必须写清楚。

**请求里的每一道菜都必须出现在 `neutralDishIds` / `unknownDishIds` / `hitList`
三者之一，恰好一次。** 见下方「输出格式」。

## User（每批填充）

```
【本批维度】
enumKey: SHRIMP_CRAB
展示名: 虾蟹类
需避免的食材: {AllergenGroups：该组 bucket=AVOID 的 displayName 列表}
易忽略的含该成分食物: {AllergenGroups：该组 bucket=HIDDEN 的 displayName 列表}

（饮食注意维度则填）
enumKey: LOW_FAT
展示名: 低脂
推荐食材: （不注入。DietRequirementRule 结构上【没有可推荐字段】，本维度不可能产生 RECOMMEND）
需避免食材: {DietRequirementContents：该规则的 avoidFoodList}
避免的菜式: {DietRequirementContents：该规则的 avoidDishPatternList}
烹饪方式建议: {DietRequirementContents：该规则的 cookingTipList}

【本批菜品】共 N 道
- dishId=10023  菠菜猪肝汤
    菠菜 150g / 猪肝 80g
- dishId=10024  白灼虾
    基围虾 200g / 姜 3g
- dishId=10025  蚝油生菜
    生菜 200g
...

（注意：上面三道菜实际都会用到调味料，但食材表里一行都没有——这就是常态）
```

> 括号里的内容由 Java 在调用前从常量类 `AllergenGroups` / `DietRequirementContents` 直接读出填充。
> **真源是 Java 常量类，没有 CSV、没有生成器、没有运行时加载**。
> **只取 `reviewStatus = REVIEWED` 的条目**；`REJECTED` 条目保留在代码和负向回归中，
> 不注入提示词，也不参与匹配。
>
> **食材表不含调味料**，见「判断范围」开头。这不是数据缺失，是食堂系统的既定口径。
>
> **食材重量是输入的一部分**（`ingredientList[].name` + `weightG`，单位克，未知给 `null`）。
> 模型输入的每个字段都必须被 `tagHash` 覆盖：直接进哈希、或由三个版本段覆盖、或是纯标识（`dishId`/`enumKey`）明确排除，
> 否则输入变了而 hash 没变，旧标签会被继续复用。

## 输出格式

**只有命中项才写完整对象，判为中立的菜只回 ID。**

```json
{
  "enumKey": "LOW_FAT",
  "neutralDishIds": [10001],
  "unknownDishIds": [10003, 10004, 10005],
  "hitList": [
    { "dishId": 10002, "verdict": "REJECT",
      "evidenceType": "COOKING", "matchedIngredients": [], "reason": "油炸菜品" }
  ]
}
```

### 覆盖要求（最重要的一条）

请求里给你的每一个 `dishId`，**必须恰好出现一次**，在三个列表之一：
`neutralDishIds` / `unknownDishIds` / `hitList`。

```
不能少：漏掉的菜会让整批作废，这一批的打标全部白做
不能多：不能出现请求里没有的 dishId
不能重：同一个 dishId 不能在两个列表里都出现，也不能在同一列表里出现两次
```

**三个列表的语义都是「我看过这道菜」，区别只在结论：**

```
neutralDishIds   我看过，能确认它不违反 / 不含
unknownDishIds   我看过，但数据不够，判不出           ← 拿不准就放这里
hitList          我看过，它违反 / 含有，证据在对象里
```

**拿不准的菜放 `unknownDishIds`，不要塞进 `neutralDishIds`，也不要省略掉。**
`UNKNOWN` 不算你判错，后端会把这道菜从推荐列表里拿掉，既不推荐也不指控它有问题。
硬凑一个 `NEUTRAL` 才是错的——那等于替厨房担保。

### `verdict` 的取值

**`hitList` 里只允许 `REJECT`，两类维度都一样。**

饮食注意维度也不产生推荐——因为仅凭食材证明不了一道菜真的低脂、低盐或低能量，
用油量和做法才是决定因素，而这些数据菜品接口给不了。
所以本模型的职责是**「挑出该拒绝的菜」**，不是「挑出该推荐的菜」。

`NEUTRAL` 与 `UNKNOWN` 都不写进 `hitList`，各自写进 `neutralDishIds` / `unknownDishIds`
——它们不需要携带证据，只有 `REJECT` 需要。
