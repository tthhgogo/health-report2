### 2.1 关于契约桩，必须说清楚的一件事

**桩证明的是「链路走得通」，不是「模型抽得准」。** 桩按 Schema 回话，
所以指标、结论、标签的**内容全无参考价值**；有参考价值的是这些内容能不能通过
Schema 校验、来源回切、章节引用、合并去重、安全扫描与四模块组装
——那一整段代码在真连跑起来之前本来一行都覆盖不到。

桩**不硬编码任何真实报告文本**：它从入参里解析出真实块号与真实文本再引用回去。
一来这样才通得过来源回切校验，二来避免把一份真实体检报告的内容固化进仓库。
姓名与性别一律返回 `null`，同一性校验因此不在本轮覆盖范围内。

### 2.2 接口走的是真实 HTTP

两个全链路用例都用 `RANDOM_PORT` + `TestRestTemplate` 发真实请求。这不是形式主义：
直接调 Controller 方法时，multipart 解析、`@Valid` 请求体校验、`@PathVariable` 绑定、
异常处理器的状态码映射、响应体序列化**全都不会执行**。已实测确认走 HTTP 后：

- 上传 / 建任务 / 轮询 / 读结果四个接口均返回 200；
- 结果响应体 **5329 字节**，Jackson 序列化正常；
- 空 `fileIds` 被 `@Valid` 拦成 **400** —— 这条断言直接调方法时根本不成立。

**真连部分没跑到不是「跳过」，是缺 9 个环境变量**（`OCR_*` / `EXTRACTION_*` / `DISHTAG_*`），
本机一个都没有。相关用例保留为显式失败，不做静默 skip。

## 3. 【F1｜高】整页内容静默丢失，且没有任何机制能发现

### 3.1 现象

解析诊断的逐页文字块数：

```
P1=68, P2=17, P3=56, P4=53, P5=40, P6=106, P7=91, P8=108, P9=100,
P10=98, P11=84, P12=90, P13=28, P14=39, P15=29, P16=2, P17=2, P18=14
```

**第 16、17 页各只有 2 个文字块**，而其余页平均 60 个以上。

### 3.2 证据

直接读 PDF 确认这两页的构成：

| 页 | 原生文本 | 内嵌图像 |
|---|---|---|
| 16 | 21 字符，内容是页脚「北京大学深圳医院 第 15 页 共 17页」 | **1653 × 2338**，整页扫描件 |
| 17 | 21 字符，同样只有页脚 | **1124 × 1466**，整页扫描件 |

也就是说：**这两页的全部报告内容都在图里，原生文本层只有一个页脚。**

### 3.3 机理

`FileParseService.parsePdf` 的路由是**整文件二选一**，不是逐页：

```java
if (pdfTextLayerChecker.hasUsableTextLayer(document)) {
    // 整个文件走原生，nativeSegmentList 一次性算完
}
// 之后每一页都用 segmentsOfPage(nativeSegmentList, page)，OCR 一次都不调
```

而 `PdfTextLayerChecker.hasUsableTextLayer` 算的是**全文档平均**：

```java
double charactersPerPage = (double) counter.getCharacterCount() / (double) pageCount;
```

16 页正常文本页把平均值拉得远高于每页 50 字符的阈值，于是整个文件判为「原生文本层可用」，
**第 16、17 页连一次 OCR 都不会被调用**。

### 3.4 为什么系统完全无感

这一条比丢失本身更值得担心。四道可能拦住它的关卡全部失效：

1. **零块裁决**：`ParseOrchestrator` 只检查「整个文件有没有 segment」，是文件级不是页级；
2. **就算改成页级也拦不住**：这两页不是 0 块，是 2 块——页脚让它们看起来「有内容」；
3. **页数预算**：`processedPages=18 / totalPages=18`，没有截断，`PAGE_TRUNCATED` 不触发；
4. **降级累加器**：`partial=false`，`partialReason=null`。

最终用户拿到的是一份**看起来完整**的结果，实际少了 2/18 ≈ 11% 的报告内容，
而且没有任何字段提示他这件事。

### 3.5 还有一层：LLM-A 看得见，但 Java 会把它扔掉

原生路径下每一页仍然会渲染图像发给 LLM-A（`ParsedPage` 带 `extractionImage`），
所以模型**能看到**第 16、17 页的扫描件内容。但设计 §7.5 要求指标的字段必须是
某个 segment 的严格子串，而这两页只有页脚 segment——

```
LLM-A 从图上正确读出检验结果
  → 找不到可引用的 segment（只有页脚）
  → 来源引用校验失败
  → 整条丢弃，evidenceMissCount++
```

模型读对了，Java 因为拿不到出处而丢掉。**唯一会留下痕迹的是 `evidenceMissCount`，
而这个计数在生产里读不到（见 F2）。**

### 3.6 为什么我没有直接改

**代码与当前设计一致，这不是实现 bug：**

- 开发方案 V1 §6.4：「PDF 是否有文本层：抽取字符数/页数 ≥ 50 且非空白字符占比 ≥ 30%」——文档级平均；
- 开发方案 V1 §6.4 表格：「文本层阈值 + 密度闸都通过 → 原生 segment；任一不过 → **整文件走 OCR**」。

`真实体检报告样本-提取逻辑验证报告.md` 的 **P0-1** 早已指出这个问题，
§9「修改顺序」第 1 条就是「修改开发方案 §6.4：所有 PDF 页都生成 OCR segment」——
**但这个修改从未落进设计方案与开发方案**，两份文档至今仍写着「整文件走 OCR」。

按 `AGENTS.md` §1，设计方案是最高真源，我不能靠一次联调就把路由从「整文件」改成「逐页」：
那会让 OCR 调用量从 0 次变成 18 次/份，是容量、成本与时延的架构级变更。

本轮的贡献是**把这个已知风险从纸面推进到实测**：不再是「样本 B 可能有问题」，
而是「样本 A 的第 16、17 页确实整页丢了，且四道关卡一道都拦不住」。

### 3.7 建议

改设计方案与开发方案 §6.4，二选一：

- **方案甲（评审报告的建议）**：每个 PDF 页都调 OCR，原生文本达标时两种 segment 并存。
  最彻底，代价是 OCR 调用量与时延。
- **方案乙（改动最小）**：路由保持整文件，但把文本层判定从**全文档平均**改成**逐页判定**，
  只对不达标的页补调 OCR。对本文件就是只多 2 次 OCR。

两个方案 Java 侧都只是「按页阈值决定要不要调 OCR」，仍然是可穷举、可单测的确定性判断，
不违反 `AGENTS.md` §3 的分层边界。

> ⚠️ 无论选哪个，都建议同时补一条**页级信号**：一页的 segment 全部来自页眉页脚时，
> 至少要能被计数或降级看见。否则换一份报告还会以同样的方式静默丢内容。

## 4. 【F2｜中】13 个生产计数全部「只写不读」

### 4.1 现象

设计方案 §9.5 与开发方案 §9.3 明确列出 13 个生产计数，并称「**这份清单就是生产环境的全部计数**」：

```
schemaMissCount、evidenceMissCount、ocrFuzzyMatchCount、allergenSuspectMissCount、
allergenPositiveUncoveredCount、allergenUnknownCount、adviceOtherCount、
sectionRefMissCount、sectionUnknownCount、highRiskSuppressedCount、
glyphLevelPdfCount、residualNonStandardCount、statusJudgedByModelCount
```

代码里这 13 个计数**都有自增点，但在 `src/main` 里没有任何一个读取点**——
getter 只被单元测试调用。既不进日志，也没有 actuator 端点或其他导出方式。

### 4.2 影响

计数器的全部意义是「出问题时能看见」。现在的状态是：进程里确实在数，但没有任何人能读到，
等价于没有。具体到本轮：

- F1 造成的条目丢弃会让 `evidenceMissCount` 增长，**这是唯一能暴露 F1 的信号**，而它读不到；
- `residualNonStandardCount`（文本污染）、`glyphLevelPdfCount`（密度闸触发）同理。

我在联调用例里显式打印了 `residualNonStandardCount`，就是因为生产侧拿不到它。
本文件的 §5 能给出「污染段数 = 0」这个结论，靠的是测试代码而不是产品能力。

### 4.3 为什么我没有直接改

加什么、加在哪、以什么形式导出（任务结束打一条汇总日志？actuator？定时快照？）
是设计决策，不是补一行代码。设计方案只规定了「有这些计数」，没规定暴露方式。
建议在设计方案 §9.5 补一节明确导出口径后再实现。

## 4A.【F3｜高·安全】高危安全闸按「整块」匹配，被排版随机切分的邻句误触发

### 4A.1 现象

用照着报告版面写的 LLM-A 替身跑样本 A，**模块四塌成完全空**（推荐 0、不推荐 0），
而数据库里明明有可用的拒绝标签：

```
ct_dish_tag: dishId=1008 红烧五花肉 / LOW_FAT / REJECT / 命中["五花肉"]
读取层返回:  dishId=1008 / LOW_FAT / REJECT
```

标签读到了，却没进裁决。

### 4A.2 根因

`HighRiskAdviceGate.HIGH_RISK_TERM_LIST` 里有 **「儿童」**。
而这条低脂建议的证据块，原文是：

```
14岁以下儿童除外)。请您戒烟忌酒,低脂、低糖饮食,控制食量,多吃蔬菜、水果
```

开头那句「14岁以下儿童除外)」**不属于这条建议**——它是上一句 BMI 公式免责说明的尾巴：

```
[101] 体重指数(BMI)=体重(Kg)/身高(M)^2;正常为18.5-24.0,>28为肥胖(孕妇和
[102] 14岁以下儿童除外)。请您戒烟忌酒,低脂、低糖饮食,控制食量,多吃蔬菜、水果
```

**PDF 的绘制单元正好切在括号中间**，把免责说明的后半截和真正的饮食建议粘进了同一个块。
安全闸做子串包含，看到「儿童」就抑制。

### 4A.3 影响链

1. 锚在该块上的 **4 条建议同时被抑制**：LOW_FAT / LOW_ADDED_SUGAR / LIMIT_ALCOHOL / LOW_CALORIE
   （模块三里 `structuredOutputSuppressed=true`，只剩原文，没有结构化内容）；
2. 在 `DishRecommendInputFactory.dimensions()` 里这 4 个维度被**整个排除**，不进裁决；
3. 剩下的 LIGHT_DIET、LOW_PURINE 对绝大多数菜是 UNKNOWN → 命中 `TagStateResolver`
   的「可拒绝维度缺数据即 HIDDEN」→ **整个模块四为空**；
4. 全程**没有任何异常日志**，`partial=false`，结果看上去正常。

### 4A.3B 两份样本的对照实验（决定性证据）

给两份样本各加了三道**同类**的清淡高纤维菜（清蒸西兰花 / 凉拌黑木耳 / 玉米糙米饭，
以及白灼芦笋 / 燕麦南瓜粥 / 清炒芹菜），规则、菜品设计思路完全一致。结果相反：

| | 样本 A | 样本 B |
|---|---|---|
| 营养补充 `DIETARY_FIBER` | **被安全闸抑制** | 未抑制 |
| 饮食注意 | 6 条中 **4 条被抑制** | 5 条全部生效 |
| 模块四产出 | **推荐 0 / 不推荐 0** | **推荐 1**（清炒芹菜「高纤维」） |

两份报告的建议原文：

```
样本 A（块 102）：14岁以下儿童除外)。请您戒烟忌酒,低脂、低糖饮食,控制食量,多吃蔬菜、水果
样本 B：          1、建议戒烟(含被动吸烟)、忌酒,低脂、低糖、低胆固醇饮食,少食动物内脏,多食蔬菜瓜果类食物
```

**唯一差别是样本 A 的证据块开头混进了「14岁以下儿童除外)」**——它是上一句 BMI 公式的尾巴，
被 PDF 绘制单元切进了同一块。词表里的「儿童」命中，于是这一块上锚着的
**5 个维度（4 个饮食注意 + 1 个营养补充）全部退出结构化链路**，模块四彻底清空。

样本 B 的同一批建议一个字的差别都没有实质不同，只因为排版没把免责说明切进来，就全部正常生效。

> 这条对照实验把 F3 从「理论上可能误触发」坐实成「已经在真实报告上发生，
> 并且完整关掉了一个产品模块」。它也顺带说明：**模块四能不能出推荐，
> 取决于 PDF 排版把哪句话切进了哪个块**——这不是任何人能预期或测试到的行为。

### 4A.4 判断

安全闸宁可错抑制，方向是对的，**问题出在匹配粒度**：

- 它匹配的是**整个被引用块**的文本；
- 而块边界是 PDF 绘制单元，**由排版决定，完全不受控**——一句话经常跨块，两句不相干的话经常同块；
- Java 只能做确定性子串包含（`AGENTS.md` §3），没法分辨「儿童」出现在免责说明里还是建议里。

于是「一句与建议无关的免责说明，只因为排版上挨着，就关掉了整个菜品推荐模块」。

### 4A.5 建议

三选一，都需要设计决策：

1. **收紧证据粒度**：Schema 增加一个「建议原文片段」字段，由 LLM-A 给出建议本身的原文
   （仍受包含性校验约束），安全闸只扫这个片段而不是整块；
2. **让抑制可见**：`highRiskSuppressedCount` 已在计数清单里，但只写不读（见 F2）。
   至少要能看出「本次有 N 条建议被安全闸抑制」，否则这类塌陷永远查不到；
3. **区分抑制范围**：命中高危词只抑制模块三的结构化内容（现状已如此），
   但**是否要连带把维度从模块四裁决里整个摘掉**，需要产品确认——
   现在这一条是隐含行为，没有在设计方案里写明。

> 无论选哪个，**第 2 条建议无条件先做**：现在这个塌陷从日志到接口返回都看不出来。

## 4B.【F4｜中·安全】部分批次被判「无体检报告特征」时没有任何降级信号

`ExtractionBatchExecutor.decide()` 的处理是不对称的：

| 批次状态 | 部分批次命中 | 全部批次命中 |
|---|---|---|
| `UNREADABLE` | `recordBatchUnreadable()` → **partial=true** | 整任务 `UNREADABLE` 失败 |
| `NO_REPORT_FEATURE` | **无任何信号** | 整任务 `NOT_HEALTH_REPORT` 失败 |

也就是说：LLM-A 只要把某一批真实数据误判成「读得清但没有体检报告特征」，
**那一批的全部页就静默消失**，`partial` 仍是 `false`，用户看到一份「完整」的结果。

本轮实测撞到了这个：替身把第 9–16 页（整个检验明细表，8 页）判成 `NO_REPORT_FEATURE`，
最终产出只剩综述建议里的 8 条异常指标，**异常率显示 100%**——而这份报告绝大多数项目是正常的。

> 替身的误判是替身的问题（已修，见 §4C），但**「误判之后没有任何信号」是系统行为**。
> 这已经是本项目第三例同一模式的静默丢失：样本 A 的图片页整页丢失、
> 样本 B 的原生文本整份丢弃、这里的整批丢弃。三处的共同点是
> **丢了多少数据，产品侧无法从任何字段或日志得知**。

建议：`NO_REPORT_FEATURE` 与 `UNREADABLE` 在部分命中时统一按 partial 处理，
或至少各自留一个可导出的计数。

## 4C.【F5｜中·展示】规范化只用于校验，展示走未规范化原文，污染字符原样呈现给用户

### 4C.1 现象

样本 B 的模块二里，同一条结论出现两种字形：

```
INDICATOR_TEXTUAL:  人纤维蛋白原降解产物(DR-70)增高      ← 干净
SUMMARY:           【1】⼈纤维蛋⽩原降解产物(DR-70)增⾼   ← 「人」「白」「高」是部首区字符
```

### 4C.2 根因

`ValidatedExtractionOutput.rawTextList()` 返回的是 `segment.getRawText()`——**未规范化的原文**：

```java
rawTextList.add(segment.getRawText());
```

它流向模块二 `SUMMARY` 条目的 `displayName`、以及模块三各卡片的来源标注 `rawText`。
而 `normalizedText` 只参与来源回切校验，从不进入展示。

样本 B 全文有 **895 处**部首区字符（65 种康熙部首 + 13 种 CJK 部首补充），
这些字符会原样出现在用户看到的结论文字里。

### 4C.3 判断

选 `rawText` 展示是**有意的**：设计方案 §5.2 规定「标签文字永远是 `conclusionText` 原文」，
不让系统的措辞误导用户。这个方向没错。

但代价在样本 B 上被放大了：`⼈`（U+2F08 KANGXI RADICAL MAN）**不是**汉字「人」，
它只是在某些字体下长得像。呈现给用户会导致：

- 换一种字体就可能显示成豆腐块或字形错位；
- 复制、搜索、朗读全部失效——用户搜「人纤维蛋白原」搜不到自己的报告；
- 同一条结论在模块二的两个来源里显示成两种字形（上面那个对比就是）。

这不是「保真」，因为这些字符本来就不是报告作者写的内容，而是 PDF 字体子集化的产物。

### 4C.4 建议

需要产品决策，两个方向：

1. **展示也用 `normalizedText`。** 规范化是保守的：NFKC + 已评审的部首映射表 + 全角转半角，
   不改变语义。代价是展示文字与报告截图逐字比对时会有差异。
2. **保留 `rawText`，但只对「确认无歧义」的污染字符做展示层替换**
   （即复用 `RadicalNormalizeMap`，不做全套 NFKC）。折中，改动面更小。

> 无论选哪个，**同一条结论不该在两个模块里显示成两种字形**——
> 现在模块二的 `INDICATOR_TEXTUAL` 与 `SUMMARY` 就不一致，这一条本身就该修。

## 4D.【F6｜已撤回】「混合分组里的正常项被丢弃」不是缺陷，是需求明文规定的行为

> **本条初稿把一个完全符合需求的行为定成了「高·数据完整性」缺陷，现予撤回。**
> 错误原因：定性之前没有回查 `体检报告分析需求.md`。

### 4D.1 我当时看到的现象

血脂4项在报告上有 4 项，产出只有 2 项；被丢掉的甘油三酯与高密度脂蛋白胆固醇
数值、单位、参考区间齐全，只是「提示」列是空单元格、本组小结又只点名异常项，
因而没有任何可引用的结论文字。我据此判断为数据完整性缺陷，并统计出「本样本丢弃 17 项」。

### 4D.2 需求怎么规定的

`体检报告分析需求.md` §5「健康指标」2）指标提取规则：

> - 仅提取报告中**有明确数值且有明确结论**的指标（如「甘油三酯 2.8mmol/L ↑偏高」）；
> - **报告中仅列数值但未给结论的指标，不在本模块展示**；
> - 报告中仅给文字结论但无数值的指标（如「肝胆B超：脂肪肝」），归入健康问题模块展示；

被丢掉的那 17 项恰好是第二条描述的情况：**有数值、无结论**。
不展示它们是需求要求的行为，链路做对了。

同 §5-5）总览条统计的是「总指标数 / 正常项数 / 异常项数 / 异常项占比」，
口径就是**本模块展示出来的指标**。所以「31 项 / 异常占比 26%」也没有失真，
我说的「双双失真」同样不成立。

### 4D.3 产品决策（2026-08-27）：有参考区间且数值在区间内，也算「有明确结论」，应当展示

撤回缺陷定性后，剩下的是「什么算明确结论」这个口径问题。产品已给出判定：

> **有参考值、并且数值在参考值范围内的，也属于有明确结论，也需要展示。**

#### 影响面（样本 A 实测）

| | 行数 |
|---|---|
| 明细表可解析行 | 94 |
| 带 `↑`/`↓` 的异常行 | 9 |
| 无箭头、有参考区间、可判定 | **49** |
| ↳ 判定在区间内（正常） | **49** |
| ↳ 判定超出区间 | **0** |
| 无参考区间（定性项目：阴性/未见异常等） | 36，仍不展示 |

**零冲突**：没有任何一行出现「Java 判超标而报告没标箭头」。
这说明区间比较不会与报告自身的标注互相矛盾，风险实测很低。

采纳后模块一：**31 项 → 48 项**（40 正常 / 8 异常 / 异常占比 17%）。血脂4项终于是完整的 4 项。

#### 落地需要改的东西

| # | 改动 | 说明 |
|---|---|---|
| 1 | **Schema：`conclusionText` 允许为 null** | 这些行报告上没有印任何结论文字，现行 `minLength: 1` 表达不了。需同时约束「为 null 时 `refRange` 必填」 |
| 2 | **来源校验放行 null** | `conclusionText` 为 null 时跳过包含性回切，其余四个字段照常校验 |
| 3 | **新增确定性区间判定** | 数值 ∈ 区间 → NORMAL，超上界 → HIGH，低于下界 → LOW；解析不了一律「无法判定」，不猜。属 `AGENTS.md` §3 允许的数值比较，必须可穷举 + 单测 |
| 4 | **展示文案走内容常量** | 需求 §5-3 要求「报告结论：直接引用报告原文结论」。这些行没有原文结论，展示什么必须由内容常量定，并在视觉上与引用原文的结论**明确区分**，否则用户会以为报告上写了这句话 |
| 5 | **同步需求与设计方案** | 见下面的冲突 |

区间格式实测出现四种破折号（`~` `～` `—` `-`）与四种单边符（`>` `<` `≥` `≤`），解析要全覆盖并各配单测。

#### ⚠️ 与需求 §5-1 的正面冲突，必须先裁决

需求 §5「健康指标」1）写的是：

> 从体检报告中提取体检结论中明确提及的指标项，**严格依据报告原文，不额外推断、补充或二次分析**；

而「数值落在参考区间内 ⇒ 正常」是**报告没说、由系统推出来的结论**。
它是确定性的、可复现的，但它确实属于 §5-1 字面禁止的「二次分析」。

两条要求现在互相矛盾，**必须改掉其中一条**，不能留着让实现自己选：

- 若采纳本决策 → §5-1 需要加例外，明确「与报告印出的参考区间做数值比较不算二次分析」；
- 展示上也要跟着说清楚：状态标签是系统判定的，不是报告原文结论。

> 在这条裁决落地前，替身里的实现用**参考区间原文**顶替 `conclusionText`
> （见 `LocalChainScriptedExtractionModel.rangeStatus` 上方注释），
> 只为把量级跑出来；它会让卡片的「报告结论」显示成 `0.91~1.55`，**不是可交付的展示形态**。

## 4E. 替身自身的两个缺陷（已修，记录以免重犯）

替身不是交付物，但它的缺陷会伪装成系统问题，所以一并留档：

| 缺陷 | 表现 | 修法 |
|---|---|---|
| 只在「综述建议解析为空」时才试明细表 | 样本 A 第 0 批同时含综述建议（2–4 页）与明细表（5–8 页），后者被整段跳过；血脂4项只剩小结点名的 2 项 | 两套版式都跑，同名分组按「明细表优先」合并 |
| 值块正则只匹配正常项的合并形态 | 异常项的数值、单位参考值、箭头是三个独立块，全部漏掉 | 按两种块结构分别采集，箭头直接用作 `conclusionText` |
| 每个分组既发指标/文字结论、又无条件补一条总检结论 | 同一条结论在模块二出现两次；样本 B 的 12 条重要异常变成 24 条 | 一个分组只产出一类：明细表→指标，综述建议/异常清单→总检结论 |

> 教训是同一个：**替身的数量特征一旦失真，就会被当成系统的产出来解读。**
> 「模块一只有 8 条」「异常率 100%」「健康问题重复两遍」这三次，
> 每一次第一反应都是「系统有问题」，实际都是替身写错了。
