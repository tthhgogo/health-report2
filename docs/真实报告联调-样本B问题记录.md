## 3. 【B-1｜高】密度闸触发，整份报告的原生文本被丢弃，23 页全部改走 OCR

### 3.1 实测

```
路由诊断，页数=23，原生文本层可用=true，密度闸阈值=400块/页，闸门触发=true，闸后保留的原生块数=0
路由诊断，最终解析路径=整文件 OCR
```

对照样本 A：

| | 样本 A | 样本 B |
|---|---|---|
| 页数 | 18 | 23 |
| 原生文本层可用 | true | **true** |
| 密度闸触发 | false | **true** |
| 保留的原生块数 | 1025 | **0** |
| 最终路径 | PDF 原生文本层 | **整文件 OCR** |
| 生产 OCR 调用次数 | **0** | **23** |

**这份 PDF 的原生文本本身是好的**：22467 个字符、每页 977 字，规范化后残留污染 = 0（§5）。
它被丢弃不是因为质量差，而是因为**绘制单元太碎**——密度闸阈值是 400 块/页，
23 页即 9200 块，实际绘制单元数超过它，说明这份 PDF 是**逐字形绘制**的。

### 3.2 后果

1. **容量与成本差一个量级。** 同样一份体检报告，样本 A 形态 0 次 OCR，样本 B 形态 23 次。
   按「通常不调 OCR」做的容量规划，遇到一批样本 B 形态的报告会直接被打穿。
2. **完全依赖 OCR 质量。** 明明有一份可用的原生文本，却一个字都不用。
3. **安全校验档位被动降级。** 来源回切在 `NATIVE` 段是**严格子串**，在 `OCR` 段走**放宽档**
   （去空白 + 编辑距离 ≤1）。整份走 OCR 意味着这份报告的每一条指标、每一个过敏原字段，
   都只受较弱的那一档保护——这是安全语义的实质变化，不只是性能问题。
4. **生产上无从得知。** 唯一的信号 `glyphLevelPdfCount` 只写不读
   （见样本 A 记录的 F2），日志里也没有任何一条能区分两条路径……

   > 更正一句：`FileParseService.logParsed` 其实**打了**「解析路径=OCR / PDF原生文本层」。
   > 所以单份任务是可追溯的。缺的是**聚合视角**——没有计数导出，
   > 就没法回答「最近一周有多大比例的报告走了 OCR」，而那才是容量规划要的数。

### 3.3 【重要修正】整份走 OCR 不是浪费，而是**必需**的

初稿这一节把「原生文本被丢弃」记成了纯粹的成本问题。后续实测推翻了这个判断：

| | 文本层中的方向箭头 |
|---|---|
| 样本 A | `↑` × 8、`↓` × 1 |
| 样本 B | **一个都没有** |

样本 B 的检验明细表用**红色图形箭头**标注异常，这些箭头**根本不在 PDF 文本层里**。
原生文本长这样（第 11 页，血脂）：

```
总胆固醇        ← 项目名
TC             ← 缩写
6.23           ← 数值
0—6.22         ← 参考区间（注意：异常描述那一格什么都没有）
mmol/L         ← 单位
```

`6.23 > 6.22` 是异常，但**文本层里没有任何字符表达这件事**。

也就是说：**样本 B 的原生文本层是不完整的**——它有数值、有参考区间，唯独没有异常标记。
只用它，模型无法知道哪些项目异常；必须看页面图像才能读到那些红色箭头。

**结论修正**：密度闸把这份 PDF 判去 OCR，恰好也是正确的选择——不是「白白多花 23 次 OCR」，
而是「不看图就读不全这份报告」。§3.2 里「完全依赖 OCR 质量」这条代价依然成立，
但「明明有一份可用的原生文本却一个字都不用」这句话是错的，**那份原生文本本来就不够用**。

这同时证实了评审报告 P0-1 对样本 B 的判断：OCR 能识别图形异常箭头，而原生文本层不能。

### 3.4 这是不是缺陷

**不是。** 密度闸正是为逐字形 PDF 设计的：逐字形 segment 一段只有一个字，
既撑不起子串校验，也撑不起 `blockRefs` 引用；而把它们合并回逻辑行需要 Y 坐标聚类，
`AGENTS.md` §3 明确禁止 Java 做这件事（阈值靠猜，双栏/上下标/跨行单元格全会翻车）。
所以「丢弃原生文本 + 整文件转 OCR」是当前分层边界下的**正确选择**。

### 3.5 建议

不改路由逻辑，但两件事必须做：

1. **容量规划按最坏情况算。** OCR 调用量的上界是「页数 × 文件数」而不是 0，
   §4.2 的并发参数 W 与配额必须按这个上界校准。建议在设计方案里把这句话写死。
2. **把 `glyphLevelPdfCount` 变成可观测的**（承接样本 A 记录的 F2）。
   它现在是唯一能告诉你「有多少报告在走贵的那条路」的数，而它读不到。

## 3A.【B-4｜高】异常项无法进入模块一：异常标记只存在于图像中

样本 B 跑完的模块一是**空的**（`totalCount=0`，空态「本次报告未提取到带明确结论的指标项」）。
其中正常项不展示是<b>需求规定</b>、不构成问题；真正的问题只出在异常项上：

| 项目类型 | 报告上的表达方式 | 为什么进不了模块一 |
|---|---|---|
| **正常项** | 「异常描述」列留空 | **按需求本就不该展示**——`体检报告分析需求.md` §5-2 规定「仅列数值但未给结论的指标，不在本模块展示」。这一条不是问题 |
| **异常项** | 「异常描述」列画一个红色箭头 | 箭头是图形，不在文本层；只有真实 OCR 看图才读得到 |

也就是说，这份报告的模块一**完全依赖 OCR 对图形箭头的识别**。
本轮的 OCR 替身是拿 PDF 文本层模拟的（见 §2.1），文本层里没有箭头，
所以替身<b>结构上无法</b>产出样本 B 的指标——这是替身的固有局限，不是解析或组装的缺陷。

> **这条必须等真实 OCR 才能验证**，而且它是样本 B 最该验的一件事：
> 如果真实 PaddleOCR-VL 读不出这些红色箭头，样本 B 这类报告的模块一会永远是空的。
> 评审报告称已实测 OCR 能识别该箭头，但那是单点实测，没有覆盖全表。

## 4. 【B-2｜已澄清】部首污染映射表对本样本已经完整

评审报告 P1-3 记的是「样本 B 检出 78 种部首字符，完整映射表未固化」，
并要求验收「样本 B 全文规范化后部首区残留数 = 0」。**本轮实测该断言成立。**

78 种拆开来看：

| Unicode 区块 | 种类 | 次数 | 处理方 |
|---|---|---|---|
| 康熙部首 U+2F00–2FDF | 65 | 739 | NFKC 自动分解 |
| CJK 部首补充 U+2E80–2EFF | 13 | 156 | `RadicalNormalizeMap` 显式映射 |
| 私用区 PUA | 0 | 0 | —— |

13 种全部已收录在现有 20 条映射里，实跑 `residualNonStandardCount = 0`。
**P1-3 可以关闭**——「约 30 条不够用」的担心在这份样本上不成立。

> 但有一处需要留意：因为 B-1，样本 B 的原生文本**根本不进链路**，
> 所以这次的「残留=0」证明的是映射表对**这份文本**够用，
> 而链路里真正需要规范化的是 **OCR 返回的文本**。OCR 文本会不会带来新的污染形态，
> 要等真实 OCR 接上才知道。

## 6. 两份样本放在一起看

这是本轮最值得记的一条：

| | 样本 A | 样本 B |
|---|---|---|
| 路由 | 原生文本层 | 整文件 OCR |
| 问题 | **图片型页面（16、17）内容整页丢失**，OCR 一次都不调 | **可用的原生文本被整份丢弃**，OCR 调 23 次 |
| 共同点 | 路由是**整文件一刀切**，没有页级中间态 | 同左 |

一个该调 OCR 的没调，一个不必全调的全调了。根因是同一个：
**路由粒度是文件级**。评审报告 P0-1 建议的「逐页判定」能解决样本 A 那一半；
样本 B 因为整份都是逐字形绘制，逐页判定救不了它，只能靠容量规划接住。
